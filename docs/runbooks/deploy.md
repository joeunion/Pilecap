**Declared blind spot: a re-deploy is proven, a reboot is not.**

*The re-deploy is proven and the trap it fell into is now refused.* The derived
project name (`djb_deploy_<8 hex of the checkout's path>`) is right, and it
ORPHANS every box deployed before it existed: a stack brought up under an older
fixed project name, met by a re-deploy that generated a fresh env file and
derived a different one, means a bare `docker compose up -d` cheerfully starts
**a second full stack beside the running one** — same box, same ports, same
database. Every `up` in this runbook is therefore
**`./deploy/provision.sh up`**, which reads
`docker compose ls`, **adopts** the project already running from this checkout
(writing its name into `.env`, so a re-deploy migrates the name instead of
forking the box) and **refuses**, exit 2, to bring a second one up beside it
unless you say `--second` and mean it.

*The reboot is still unproven.* `deploy/.env` is written by step 31 and lives
only on the box's disk, so an instance that restarts comes up with no
environment for compose to substitute from. Unchanged, and the first person to
reboot a box is finding out, not confirming.

*What `provision.sh up` cannot see, declared:* it reads `docker compose ls`, so
a stack somebody started with `docker run` by hand, or with a compose file from
another path, is not seen. **And it deliberately does not look at `web` or
`worker` at all**: it brings the pair up with `--no-recreate` and has
no opinion about which image they are running, because moving them onto the new
one is release act 6's job, after the migrate. So `up` alone cannot tell you the
box is serving the new tree, and it does not claim to — step 37 is what makes
that true, and `docker inspect … --format '{{.Config.Image}}'` is what witnesses
it.

**Where the neighbouring subjects live**, named here so nobody writes a second
copy: observability is **Part 9 of this file**, with the surface itself in
`deploy/observability/`; the email mechanism is "Email mechanism", below Part 7
(the template operates no sender of its own, so there is nothing to warm up);
the other two transports and the signing recipes are "The other transports: SMS
and push" and "Signing a status webhook by hand", between Part 7 and Part 8 —
written here because an answer that lives only in a code comment and a test
file is not where an operator looks; alerts and escalation are
`docs/runbooks/alerts.md`; backup and restore is
`docs/runbooks/backup-restore.md`.

## Declared seam: how `web` and `worker` get their secrets

**Today both containers use `file:` mode, and that is a deliberate, recorded
seam rather than a shortcut.** `deploy/entrypoint.sh` supports two values for
`DJB_SECRETS_SOURCE`:

| Mode | What it does | Works today? |
|---|---|---|
| `file:<path>` | sources an env file the box already holds | **yes** — this is what steps 31–34 use |
| `aws:<prefix>` | fetches each secret from Secrets Manager at container start | **no** — see below |

`aws:` mode shells out to the AWS CLI, and **the runtime image does not carry
one**: `Dockerfile`'s runtime stage installs `curl` and nothing else, so
`command -v aws` fails and the entrypoint exits 2 with that exact message
rather than starting on a half-materialized environment. Step 29 therefore
fetches on the *host* — `provision.sh secrets-fetch`, as the instance role —
and writes `deploy/.env` mode 600, which `teardown.sh` removes.

**What this costs, stated plainly:** the app's own secrets land on the box's
disk instead of living only in the container's memory, which is the one thing
ADR deploy-3(b) wanted to avoid. The organs' credentials were always going to
be in that file (compose has no vault client), so the seam narrows rather than
opens a hole — but it is a real difference from the ADR, stated here rather
than discovered at step 34. Closing it is one line in the runtime stage of
`Dockerfile`, and it is a decision rather than an edit: an AWS CLI in the app
image is ~50MB and a supply-chain surface, and the alternative
(a one-shot `amazon/aws-cli` sidecar writing to a shared volume) reaches the
same disk anyway.

## Part 0 · Before you start

**1. Have the tools.** `docker` (with `docker compose` v2), and for parts 2–8
`aws` (v2, authenticated) and `ssh`. Check:

```bash
docker compose version
aws sts get-caller-identity        # parts 2–8 only
```

**2. Have the repository.** Parts 1 and 3–8 all run from a checkout — the
release tooling (`release.sh`, `provision.sh`, `ship.sh`) lives in it, and
`deploy/` is bind-mounted into the containers. The compose file builds
nothing (ADR deploy-4): images are pulled from the registry by tree tag.

```bash
git clone <this repository> && cd <the checkout>
```

**3. Know which environment you are performing.** `laptop`, `staging` or
`prod`. It is the argument to almost everything below. The names, sizes and
lifecycles are in the cycle plan's environments contract; the short version:
`staging` is standing, `prod` is ephemeral and torn down after its evidence.

```bash
export DJB_ENV=staging            # or laptop, or prod
```

**4. Know this deployment's namespace.** One slug, and every AWS coordinate
below is composed from it: the Secrets Manager prefix
(`$DJB_DEPLOY_NAMESPACE/$DJB_ENV/env`), the two buckets, the two IAM roles, the
EC2 tags, the RDS identifier, the directory the tree lands in on the box and the
alert bundle's name. **It has no default and unset is a refusal** — the same
grammar `deploy/dns.sh` uses for `DJB_ZONE_ID`, and for the same reason: a
guessed namespace is not an error, it is a correct-looking write into somebody
else's resources. It is a slot in this environment's vault blob
(`deploy/env.staging.example` ships the name and the argument, never a value),
so on the box `set -a; . deploy/.env; set +a` exports it after step 31. On the
laptop, for parts 2–8, export it yourself:

```bash
export DJB_DEPLOY_NAMESPACE=<this deployment's namespace>
```

**5. Read what you are about to spend.** `deploy/provision.sh infra` creates
billable resources and refuses without `--confirm`. Re-price every line against
today's list price before you run it (the shop-the-price duty), and ping the
owner BEFORE creating anything that is more than 10% off the approved table.

**6. A product, once: the platform reviewed by its owner.** Copy
`.github/CODEOWNERS.template` beside itself without the `.template` suffix —
`CODEOWNERS`, product-owned (`python -m quality.djb.rituals.divergence
--codeowners <that path>` writes it from the product's own tree) — and
replace `@OWNER`. Then the product's owner — never an agent
— sets three fields on the default branch's ruleset `pull_request` rule:
`require_code_owner_review: true`, `required_approving_review_count: 1`,
`dismiss_stale_reviews_on_push: true`. Know what that leaves uncovered: the
stack files (`pyproject.toml`, `uv.lock`, `compose.yaml`, any
`compose.*.yaml`, `.env.example`) and the shared paths (the file's unowned
lines, `.secrets.baseline` beside them) have NO code owner — they are reviewed
only by the one approving review and, for the stack, by the `Layer-Sanction:`
trailer a commit there must carry. The template itself sets none of the three
fields: its one human cannot review his own pull request (house rule 95).

## Part 1 · The laptop proof

**0. Preflight — every precondition of the walk, at minute zero.** From the
laptop, as yourself, with Part 0's exports and the ones steps 16–20 name. It
only READS — describe, get, head and list; it creates, puts and tags nothing,
and costs nothing — so it is the one AWS call before the proof below. Each
check prints one line naming the step it guards and that step's command, and
a refusal ends with the one line that fixes it: the env file's four slots
(16), `DJB_OWNER_IP` (20), the key pair (18), the two bucket names free or
yours (22), the box role and its inline `djb-box` naming exactly this
environment's buckets and secret (19), the three repositories and this tree's
image in them (19a, 33), the secret (17), the release's operator account
(37), the zone and the site's record (26).

```bash
./deploy/provision.sh preflight "$DJB_ENV"          # reads deploy/.env; a second argument names another file
```

Exit 0 every check ok · 1 one or more `REFUSED` (fix each, re-run) · 2 a check
could not be made — `aws` answered neither yes nor no, and its stderr is on the
`ERROR` line; 2 outranks 1. **Run it again after every take**: a refusal fixed
at step 22 is three hours cheaper than the same refusal met at `release.sh`.

The box's own `docker login` is the one check the laptop cannot make: the
registry credential is the box's. The laptop run says so on its
`not checked here` line, which names the box-side half:
`./deploy/provision.sh preflight <env> --on-box`, run on the box once step 30
has shipped the tree there.

**No AWS. No account. No cost.** This is the whole deployment — web, worker,
Caddy, Temporal, Zitadel, Redis, the collector and ClickStack — on one machine,
and it is how you find out whether a change to `deploy/` works before you find
out on a box at cloud latency. Run it before every performance of parts 2–8.

**The stack is this CHECKOUT's, and nothing threads that through the commands
below.** The compose project name is derived from the checkout's path —
`djb_deploy_<8 hex>`, the same shape and the same hash `scripts/db.sh` gives
this checkout's database — and `provision.sh env-file` writes it into
`deploy/.env`, which compose reads by itself. So a bare `docker compose -f
deploy/compose.yaml …` run from two different worktrees touches two different
sets of containers, networks and volumes. It did not always: `compose.yaml`
pinned one name for every checkout, and `teardown.sh local --purge` in one
worktree took another worktree's data with it.

```bash
./deploy/provision.sh project-name          # the name THIS stack carries
./deploy/provision.sh derived-project-name  # the name this CHECKOUT derives
./deploy/provision.sh image-tag             # what its images are tagged
docker compose ls                           # every stack on this machine
```

**The two answers are not always the same string, and the difference is a real
box.** `provision.sh up` ADOPTS the name of a stack that was already running
from this checkout and writes it into `deploy/.env` — so a box whose stack
predates the derivation carries `djb-deploy`, and the derivation still says
`djb_deploy_<8 hex>`. `project-name` answers what the stack carries (an
exported `COMPOSE_PROJECT_NAME` first, then `deploy/.env`, then the
derivation); `derived-project-name` answers only the derivation, which is what
`teardown.sh` compares against to decide whether a project is this checkout's
to destroy. **Use `project-name` everywhere you are naming a live thing** — a
network, a container label. Answering the derivation on an adopted box is how
step 12's psql container ends up joining a network that does not exist.

**A second stack from the same checkout** — a restore drill needs one — is
`COMPOSE_PROJECT_NAME=<name>` (or `-p <name>`), which outranks everything. Host
ports are the other half of that, and they are the restore drill's
ports-override file, not this runbook's. `teardown.sh` accepts such a name only when Docker's own
`com.docker.compose.project.working_dir` label says this checkout brought the
stack up; anything else it refuses, exit 2, without stopping or removing
anything.

**5. Generate the environment.** Every secret, by machine, into a file mode
600. Nothing is typed and nothing is copied from `.env.example`.

```bash
./deploy/provision.sh env-file deploy/.env laptop
```

It prints the observability wall's password **once**. Keep it or lose it; it
is stored nowhere, and re-running this step generates a whole new environment.

**6. Check the belt over what it generated.** Silence is the pass.

```bash
./deploy/assert_not_published.sh deploy/.env
```

**7. Build the three images — ON THE LAPTOP AND ONLY ON THE LAPTOP.**

```bash
export DJB_IMAGE_TAG="$(./deploy/provision.sh image-tag)"
docker build --target web    -t "$(./deploy/provision.sh image-ref web)" .
docker build --target worker -t "$(./deploy/provision.sh image-ref worker)" .
docker build --target frontend -t "$(./deploy/provision.sh image-ref frontend)" .
```

**`deploy/compose.yaml` has no `build:` and this is not a `compose build`** —
that is ADR deploy-4, and it is the whole change: **the image for a tree is
built once, in CI, multi-arch, and pushed; every box pulls it.** What you are
doing here is the one exception the ruling names — a laptop proving *this
compose file and these settings* against an image that never leaves the laptop.
The env file the previous step generated pins `DJB_IMAGE_REGISTRY='local'`, so
these three names (`local/djb-web:tree-…`, `local/djb-worker:tree-…`, `local/djb-frontend:tree-…`) are purely
local and no registry is consulted for them.

**A locally built image can never be released.** `deploy/release.sh` resolves
the tree tag in the registry before its first act and refuses, exit 2, a tag the
registry does not have — so nothing you build here can reach a box, which is
what makes this exception safe rather than a hole.

`DJB_IMAGE_TAG` is the tree hash, so the images say which tree they came from
and no tag is `latest`. `deploy/.env` carries the value that was current when
you generated it; re-export it whenever you rebuild, and keep it exported for
`up`, `run` and `restart` in the steps below.

**8. Bring the deployment up.**

```bash
./deploy/provision.sh up --profile laptop
```

**Not a bare `docker compose up -d`, and that is the whole point.** `provision.sh up` reads
`docker compose ls` first: with nothing running it brings up the name in
`deploy/.env`; with this checkout's stack already running it **adopts** that
name and writes it into `.env`; with a different `COMPOSE_PROJECT_NAME`
exported it **refuses**, exit 2, naming the running project. Everything after
`up` in the command line is passed through to compose, so extra `-f` files and
`--profile` go where you would put them anyway.

`--profile laptop` adds one service and only one: a Postgres container standing
in for RDS. Everything else is exactly what a box runs — **including
`readyz-prober`**, which is a service in `deploy/compose.yaml` rather than an
override file, so the outage and deaf-sink alert paths are armed on every
deployment instead of only when somebody remembers a second `-f`
(`docs/runbooks/alerts.md`).

**A SECOND STACK ON THE SAME LAPTOP** — a restore drill, or two builders on one
machine — adds `deploy/compose.second.yaml`, which parameterises the only
published ports there are (Caddy's). Name the project with `-p` and pick the
ports; nothing in `deploy/compose.yaml` changes, and the file is a no-op when
the variables are unset:

```bash
DJB_HTTP_PORT=8080 DJB_HTTPS_PORT=8443 \
  docker compose -p djb-b1b \
  -f deploy/compose.yaml -f deploy/compose.second.yaml \
  --profile laptop up -d
```

Every `docker compose` line in this part is then that project's rather than
this checkout's derived one. **The two lines that ASK for the project name —
step 9's `--filter` and step 12's `--network` — read it from
`./deploy/provision.sh project-name`, which answers with an exported
`COMPOSE_PROJECT_NAME` where there is one and knows nothing about a `-p` you
typed.** So `COMPOSE_PROJECT_NAME=djb-b1b` in the same shell makes both lines
right; for a stack named with `-p` alone, substitute the name you gave it
(`--network djb-b1b_default`). Everything else in this part needs no change:
compose takes the project from `-p`, and those two lines are the only place a
name is spelled out at all.
`https://localhost:8443` is that stack's edge. The full two-stack drill is
`docs/runbooks/backup-restore.md`.

Tearing such a stack down is `COMPOSE_PROJECT_NAME=djb-b1b ./deploy/teardown.sh
local --purge`, **from the checkout that brought it up** — `teardown.sh` proves
that from Docker's own `com.docker.compose.project.working_dir` label and
refuses, exit 2, from anywhere else.

**9. Wait for every organ.** Temporal migrates two schemas on a first start and
Zitadel bootstraps its first instance; two minutes is normal.

```bash
docker ps --filter "label=com.docker.compose.project=$(./deploy/provision.sh project-name)" \
  --format '{{.Names}}\t{{.Status}}'
```

The filter is the compose **project label**, not a name prefix: `--filter
name=djb-deploy` would match another checkout's containers as happily as your
own, which is the collision the project name now prevents.

Expect `healthy` for `db`, `redis`, `temporal`, `zitadel` and `web`.
`clickstack`, `otel-collector`, `caddy`, `worker` and **`readyz-prober`**
declare no health check and show `Up`. **Ten containers on a laptop**
(`--profile laptop`), **nine on a box** (no `db` — that is RDS); an eleventh,
`alerts-dummy`, only when you add
`-f deploy/observability/alerts/compose.sink.yaml`, which is laptop-only by
construction. Counted off `deploy/compose.yaml`'s service list, not recalled:

```bash
# PRECONDITION: deploy/.env must exist (step 5 on a laptop, step 31 on a box).
# `deploy/compose.yaml` interpolates required variables with `${X:?...}`, so
# without it compose FAILS — and `wc -l` turns that failure into `0`, a number
# shaped exactly like an answer. Check first, then count:
test -f deploy/.env || echo "no deploy/.env — the counts below will read 0, which is not a count"

docker compose -f deploy/compose.yaml --profile laptop config --services | wc -l   # 10
docker compose -f deploy/compose.yaml config --services | wc -l                    # 9 (a box)
```

**`--profile laptop` is what makes the first one say 10**: without it compose
resolves the profile away and `db` is not in the list, so the command printed 9
beside a sentence claiming 10. The two lines above are the
two numbers, each with the flag that produces it.

**And a `0` from either line is never a count** — it is compose refusing to
interpolate, with `wc` swallowing the message. That is the shape this runbook
refuses everywhere else: a pipe that replaces an exit status with a plausible
number. Drop the `| wc -l` and read what compose actually said.

`readyz-prober` says what it is doing on its first two log lines, and says
**out loud** when the deaf-sink half is disarmed because `SLACK_WEBHOOK_URL` is
empty:

```bash
docker compose -f deploy/compose.yaml --profile laptop logs readyz-prober --tail 3
```

**Steps 10–14 are Part 5's acts, walked one at a time.** On a real deploy they
are one command (`./deploy/release.sh`, step 37); here they are separate on
purpose, because the laptop proof exists so a person can *watch* each act and
recognise its output later. Read them as the annotated version of what that
script does, and note that acts 1, 2 and 3 below are the ones whose ORDER
matters: the grants bind the tables that exist when they run.

**10. Migrate, as the schema owner.** The application's role cannot create a
table — that is the point of step 11 — so this one command runs as the master.
The two `-e` flags have no `=`: the values travel in the environment and never
in `ps` or in your shell history.

**Every `compose run` in this runbook names `oneoff`, and never `web` or
`worker`.** `oneoff` is a service in `deploy/compose.yaml` that is never `up`'d:
it runs the same image with the same entrypoint, sets `DJB_SERVICE_NAME=oneoff`
so the settings module derives a connection pool of **2** instead of web's
**20**, and declares no `depends_on` so a one-off on a loaded box never tries to
(re)start an organ. It exists because a one-off that ran as `web` reserved a
deployment's worth of connection slots and got refused on a busy box —
`revoke_token` timed out with zero slots free, and the release acts are the same
shape. If you type a one-off of your own, type `oneoff`;
`quality/tests/deploy/test_release.py` censuses this file and refuses a `run … web` that
creeps back in.

```bash
set -a; . deploy/.env; set +a
DATABASE_USER="$POSTGRES_USER" DATABASE_PASSWORD="$POSTGRES_PASSWORD" \
  docker compose -f deploy/compose.yaml --profile laptop \
  run --rm -T -e DATABASE_USER -e DATABASE_PASSWORD oneoff \
  python manage.py migrate --noinput
```

**11. Generate the release SQL** — the app's role, its privileges, and the
revoke on every append-only table. The population is read off the model
declarations; nothing here is a list.

```bash
docker compose -f deploy/compose.yaml --profile laptop \
  run --rm -T oneoff python /deploy/grants.sql.py --role "$DATABASE_USER" --create-role \
  > /tmp/djb-grants.sql
cat /tmp/djb-grants.sql
```

**12. Apply it**, as the schema owner. **The psql client image is the one
`deploy/compose.yaml` pins for `db`** — this step said `postgres:16.10` while
that file pinned `postgres:18.6`, two majors apart in two files nobody diffs
against each other. `release.sh` now *reads* the pin rather than carrying a
copy of it.

```bash
PGPASSWORD="$POSTGRES_PASSWORD" \
docker run --rm -i --network "$(./deploy/provision.sh project-name)_default" \
  -e PGPASSWORD -e DATABASE_USER -e DATABASE_PASSWORD -e PGSSLMODE postgres:18.6 \
  psql -h "$DATABASE_HOST" -p "$DATABASE_PORT" -U "$POSTGRES_USER" -d "$DATABASE_NAME" \
       -v ON_ERROR_STOP=1 -f - < /tmp/djb-grants.sql
```

**13. Restart the app**, so it reconnects as the role that now exists.

```bash
docker compose -f deploy/compose.yaml --profile laptop restart web worker
```

**14. Ask it whether it is alive and whether it is ready.**

```bash
curl -sk https://localhost/healthz    # {"status": "ok"}
curl -sk https://localhost/readyz     # {"db": true, "cache": true, "channel_layer": true, "temporal": true}
```

`-k` because the certificate is from Caddy's own internal CA on a laptop; on a
box it is Let's Encrypt's and `-k` comes off. Read the certificate if you want
to see which:

```bash
echo | openssl s_client -connect localhost:443 -servername localhost 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

**15. Drive the worked example through the REST door.** This is the probe: a
row created through a real door, over TLS, by a real credential.

```bash
docker compose -f deploy/compose.yaml --profile laptop \
  run --rm -T oneoff python manage.py seed --force
docker compose -f deploy/compose.yaml --profile laptop \
  run --rm -T oneoff python manage.py issue_token \
  --email owner@example.com --tenant acme --name laptop-proof \
  --scope widgets:write
# `--scope` is required — a token is minted with a stated reach, never a
# default one. `widgets:write` is all this probe needs and it covers both
# calls below: within a section the write scope includes the read.
# paste the token that prints:
TOKEN=<the token>
curl -sk -X POST https://localhost/api/v1/widgets/ \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"name": "laptop proof"}'
curl -sk https://localhost/api/v1/widgets/ -H "Authorization: Bearer $TOKEN"
```

`seed --force` exists because `DEBUG` is off here and `seed` creates accounts
whose passwords are published in this repository. **Never run step 15 against
`staging` or `prod`** — parts 6 and 7 use real identity instead.

To take the laptop proof down: `./deploy/teardown.sh local --purge`.

## Part 2 · Provision

**16. Generate the environment for this deployment.** `DJB_DOMAIN` is the
domain `deploy/dns.sh` names the records under (step 26's), so the env file and
DNS agree: the site is `$DJB_ENV.<your domain>`, with `auth.` and `o11y.` before
it. Unset, the generator refuses.

```bash
DJB_DOMAIN=<your domain> ./deploy/provision.sh env-file deploy/.env "$DJB_ENV"
```

**17. Store it in Secrets Manager**, under this environment's own prefix.
Nothing is shared between environments — not one value.

```bash
./deploy/provision.sh secrets-put "$DJB_DEPLOY_NAMESPACE/$DJB_ENV/" deploy/.env
```

**18. Create the EC2 key pair.** The old step 18 said `<your EC2 key pair
name>`, which is a step that asks you to already have done a step. Free, and

**After a take that changes the rendered `djb-box`, re-run

**READING THE PUSH SCAN, AND THE ONE THING THAT SURPRISES EVERYBODY.**
`scanOnPush=true` is set above, and **asking about the TAG returns
`ScanNotFoundException`** — measured, not guessed, on the first real push. A
multi-arch tag names a manifest *list*, and ECR scans the concrete child
manifests, not the index. So resolve the index first:

```bash
aws ecr describe-images --repository-name "$DJB_DEPLOY_NAMESPACE/djb-web" \
  --region "$AWS_REGION" --query 'imageDetails[?!imageTags].imageDigest' --output text
aws ecr describe-image-scan-findings --repository-name "$DJB_DEPLOY_NAMESPACE/djb-web" \
  --region "$AWS_REGION" --image-id imageDigest=<one of those> \
  --query 'imageScanFindings.findingSeverityCounts'
```

**And know what the scan is telling you about.** The gate's supply-chain leg is
`pip-audit` plus licences — it reads this project's *Python* dependencies. This
scan reads the **operating-system layer of the base image**, which nothing in
this repository has ever looked at, because until the registry move nothing ever pushed
an image to a registry that scans. A non-zero count here is not a regression;
it is a surface that was always there and is now visible. Treat it as its own
queue item with its own owner, never as something to silence in passing.

**WHAT THIS STEP COSTS, priced rather than assumed.** ECR storage is per
gigabyte-month; two images per tree at a few hundred megabytes each, one tree per
merge, is dollars a month and it grows without a lifecycle rule.

**THERE IS NO LIFECYCLE POLICY, AND THAT IS A RULING RATHER THAN AN OMISSION**
(owner, 2026-08-31). The trade is real in both directions: a rule keeps the bill
flat, and **an expired image is a tree you can no longer roll back to** (Part 10,
step 59 — `image-digest` refusing there is exactly this). The ruling takes
**rollback-forever over storage growth**, because at one merge per tree the bill
is small and the 3am case is not.

**The residual, and its trigger:** revisit when **ECR storage becomes a visible
line on the bill**, or when **a third product shares this account** — either
makes the growth somebody else's problem as well as this deployment's. Until one
of those happens, do not add a rule "to be tidy": you would be trading a
capability you can measure for a cost you cannot yet see.

**30. Ship the tree to the box.** The release tooling runs from it and
`deploy/` is bind-mounted into the containers, so the checkout is part of the

**Not `git clone`.** The old step said to clone, and on a private repository a

so it failed as written. Pushing the tree over the ssh connection you already
have is the shorter path and adds no long-lived credential to the box:

```bash

./deploy/ship.sh ec2-user@"$BOX_IP" --key ~/.ssh/$DJB_DEPLOY_NAMESPACE-$DJB_ENV.pem
```

`git archive HEAD` — which is what the script builds — ships exactly the tracked
tree: no `.git`, no `.venv`, and no `deploy/.env`, which step 31 creates on the
box from the vault. The box gets the code and none of the history, which is the
right amount for something whose job is to run it.

**IT USED TO BE ONE LINE, AND THE ONE LINE SHIPPED A TREE THAT WAS NOT THE TREE
IT NAMED.** What was written here was
`git archive … | ssh … 'mkdir -p "$NS" && tar -x -C "$NS"'`, and **`tar -x`
overlays**: it writes every file in the archive and deletes nothing. A file
removed upstream survives on the box while the `TREE` marker beside it names the
new tree. LOAD-1a measured it on staging — 1119 files carrying the tag of a
1117-file tree, the core app's `storage.py` and its test still sitting there two
commits after they were deleted.

**And it is sharper here than on most deployments**, because `INSTALLED_APPS` is
discovery-derived: a surviving `apps/<x>/apps.py` is not a stale file, it is an
app this tree deleted being installed again, with its routes, its models and its
migrations, and nothing in the release, the gate or `/readyz` able to see it.

So `ship.sh` extracts into a **fresh location** (`$DJB_DEPLOY_NAMESPACE.incoming`,
removed first), **verifies the landed file set against the archive's own
manifest**, and only then swaps it into place — keeping the tree it replaced at
`$DJB_DEPLOY_NAMESPACE.previous`, which is what makes the rollback in Part 10 a re-ship rather
than an improvisation. **The exit status is the verdict**: `0` the tree landed
and matches · `1` it landed and does NOT match, and **nothing was swapped** —
the box goes on serving what it was serving · `2` refused, or the box could not
be read. Read it before you run it with `--dry-run`; drive it with
`./scripts/test.sh quality/tests/deploy/test_ship.py`.

`--add-virtual-file=TREE:…` is still how the tree names itself on a box with no
`.git` (below), and the script derives that tag from
`./deploy/provision.sh image-tag` rather than owning a second copy of it. It
**refuses a dirty checkout, exit 2**: `git archive` ships the committed tree, so
a `-dirty` tag would put clean bytes on the box under a name saying otherwise.
Commit, or name the tree you mean with `--ref <sha>`.

**`--add-virtual-file=TREE:…` is the second half, and it is N121b.** Shipping no
`.git` also leaves the box with no repository to ask *which tree is this*, so
`provision.sh image-tag` printed `untracked`, the box built `djb-web:untracked`,
and this deployment's own "every image is pinned to a tree" claim was false on
the only machine it mattered on, and the tag had to be pinned by hand. Now it is derived
**where git is** — on your laptop, by the same function — and carried in the
archive as a `TREE` file beside `deploy/`. **Git still wins where git
exists**, so a laptop is unchanged and a checkout can never be fooled by a stale
`TREE` somebody left behind; `TREE` answers only where the repository does not.
`untracked` survives as the last resort and now means what it says: no git AND
no archive marker, i.e. somebody assembled this tree by hand.

**`TREE` IS LINE-ORIENTED, AND ITS FIRST LINE IS THE TAG.** It used to be one
line read as "the whole file with the whitespace taken out", which is a reader
that cannot survive the file growing a second line — and it grew one:
`release.sh` now pins the released image **digest** beside the tag (ADR
deploy-4). So the grammar is stated rather than assumed: **line 1 is the tag,
bare; every later line is `<key> <value…>` and is read by key, never by
position.** A box shipped before this change carries a one-line `TREE` and is
read correctly by the same code.

```
tree-a1b2c3d4e5f6
digest web sha256:…
digest worker sha256:…
```

Read them with `./deploy/provision.sh image-tag` and
`./deploy/provision.sh tree-digest web`. Nothing writes the digest lines but
`release.sh`, and it writes them only after the containers are actually on that
image — the file records what this box **released**, not what somebody intended
to release.

`--add-virtual-file` needs git ≥ 2.38, and `ship.sh` refuses (exit 2) on an older
one rather than shipping a box that cannot say what it is holding.

**A deploy key is the alternative, and it was not taken.** A read-only GitHub
deploy key on the box makes `git pull` work and makes redeploying one command —
and it also puts a credential with permanent read access to the source on a
machine with a public IP, which the ephemeral-environment posture (ADR
deploy-1) does not want. Stated so the next performer can disagree deliberately
rather than by accident.

**ON A RE-DEPLOY, RUN THIS STEP — DO NOT HAND-COPY `deploy/.env` ACROSS.** The
archive deliberately does not carry it (step 30), so the obvious move when
swapping in a fresh tree is `cp old/deploy/.env new/deploy/.env`. That copy
loses the file's GROUP. `secrets-fetch` writes it `chgrp 10001, mode 640`
because `web` and `worker` read it as uid 10001 while compose reads it as you;
a hand-copy leaves it `600` owned by your login, and **every app
container then restarts for ever** with one line and no explanation:

```
/deploy/entrypoint.sh: line 132: /deploy/.env: Permission denied
```

Seen on a real box. `ls -ln deploy/.env` should show group
`10001` and mode `-rw-r-----`; if it does not, re-run this step.

## Part 4 · Deploy

> **A RE-DEPLOY OF A BOX THAT ALREADY EXISTS IS ONE COMMAND, AND IT IS NOT THE
> STEPS BELOW.** `deploy/stage.sh` owns Parts 4 and 5 together for that case —
> ship, the env file from the vault, the registry login, `provision.sh up` and
> `release.sh`, in that order, **each act keyed on its own input** and each
> printing its seconds:
>
> ```bash
> ./deploy/stage.sh <user>@<host> --env <environment> [--key <identity>]
> ./deploy/stage.sh <user>@<host> --env <environment> --dry-run   # say what would run
> ```
>
> It reads the box's own `TREE` marker and this checkout's tree, and runs the
> ship when the tag moved, the secrets fetch when the ship ran, the login and
> the `up` when the tag or the image digest moved, `release.sh` when a
> migration leaf, `deploy/observability/` or an image digest moved, and the
> readiness probe always. A tree whose whole delta is inert deploys nothing and
> says so. Exit 0/1/2 mean what they mean everywhere here, and a piped stdout
> is refused. It derives `DJB_IMAGE_REGISTRY` from `provision.sh image-repo`
> and carries it to the box, which is the slot neither the vault nor
> `deploy/.env` holds.
>
> **The steps below are still the authority on WHAT each act is and why**, and
> they are what a FIRST deploy walks: a box with no `TREE` marker is a refusal
> in `stage.sh`, by design, because "unchanged" and "never deployed" are not
> the same sentence. Rollback is unchanged too — `deploy/ship.sh --ref <sha>`
> and then a release (Part 10).

**32. Set the ACME account email.** `CADDY_TLS` is `internal` on a laptop and
an email address in a real environment; the address is the Let's Encrypt
account expiry notices go to.

```bash
python3 deploy/envfile.py set deploy/.env CADDY_TLS '<an address a human reads>'
sudo chgrp 10001 deploy/.env && chmod 640 deploy/.env
./deploy/assert_not_published.sh deploy/.env
```

`envfile.py set` rewrites the line in place and keeps the file's inode, so step
31's group 10001 and mode 640 survive it; the `chgrp`/`chmod` line re-asserts
them. **Never `sed -i` it** — that writes a new file owned by your login and
the app containers restart on `Permission denied` (step 31).

**33. Confirm the box can GET the image for this tree. IT DOES NOT BUILD ONE.**

```bash
cd ~/"$DJB_DEPLOY_NAMESPACE"
export DJB_IMAGE_TAG="$(./deploy/provision.sh image-tag)"
echo "$DJB_IMAGE_TAG"                        # tree-<12 hex>, NEVER `untracked`
./deploy/provision.sh image-ref web          # <registry>/djb-web:tree-<12 hex>
aws ecr get-login-password --region "$AWS_REGION" \
  | docker login --username AWS --password-stdin \
      "$(echo "$DJB_IMAGE_REGISTRY" | cut -d/ -f1)"
./deploy/provision.sh image-digest web       # the registry's answer, sha256:…
./deploy/provision.sh image-digest worker
```

**THIS STEP USED TO BE A BUILD, AND THAT WAS THE DEFECT (ADR deploy-4).** The
box is Graviton, so it built its own arm64 image — a *third* build of the same
tree, after CI's two, on the slowest and least debuggable machine in the system,
with nothing anywhere able to say whether it matched the amd64 image CI had
proved. **One image per tree now, built once, in CI, `linux/amd64` and
`linux/arm64` in one manifest, pushed under the tree tag.** The box pulls it;
staging and prod pull the *same* digest; promotion is a re-pin and never a
rebuild.

**If `image-digest` refuses (exit 2), STOP — do not build anything.** It means
one of two things and both are worth knowing before you go further:

* **this tree never reached a green CI run.** The images job runs `needs: gate`,
  so an ungated tree has no registry tag by construction. Push the tree, wait
  for the gate, come back.
* **the daemon is not logged in to the registry** — a 401, which `image-digest`
  names and answers with the login line above (the token lasts twelve hours).
* **this box is pointed at the wrong registry.** `grep DJB_IMAGE_REGISTRY
  deploy/.env` — it is the repository prefix
  (`<account>.dkr.ecr.<region>.amazonaws.com/<namespace>`), it has no default,
  and an empty slot is a refusal rather than a guess.

**If `image-tag` says `untracked`, stop** for the older reason: the archive was
made without `--add-virtual-file` and this box cannot say which tree it is
holding. Re-run step 30.

**No `--profile laptop`.** Postgres is RDS here; the `db` service does not
start and must not.

**THE TAG YOU EXPORT HERE IS NOT THE TAG THAT RUNS.** `deploy/compose.yaml`
interpolates `${DJB_IMAGE_REGISTRY}/djb-web:${DJB_IMAGE_TAG}` out of
**`deploy/.env`**, and step 31 just restored that file from the vault carrying
the tag stored at the LAST deploy. So a re-deploy could pull a new image and
then start the old one — nothing fails, `/` serves the previous tree, and the
only witness is `docker inspect`.

Step 34 reconciles it: `provision.sh up` compares the env file's pin against
`provision.sh image-tag` (the tree on this box), **adopts the tree's tag** and
says so, **pulls** the image if this box does not have it yet, and **refuses,
exit 2**, when neither this machine nor the registry has it. Check it yourself
with:

```bash
docker inspect $(docker compose -f deploy/compose.yaml ps -q web) \
  --format '{{.Config.Image}}'      # must end in the tag `image-tag` prints
```

**And re-store the environment afterwards** (`provision.sh secrets-put`), or the
vault keeps the stale tag and the next `secrets-fetch` reintroduces it.

**34. Bring it up.**

```bash
./deploy/provision.sh up
```

**On a re-deploy this is the step that does not fork the box** (see the
blind-spot note at the top of this file). It prints which of the three things
happened — `no stack from this checkout is running`, `adopting the running
project <name>`, or `project <name> (already running, and the env file agrees)`
— and a deliberate second name beside a running stack is refused, exit 2, with
the running project named. That refusal has one escape and it is a sentence you
have to type on purpose: `COMPOSE_PROJECT_NAME=<name> ./deploy/provision.sh up
--second`, which is the restore drill and nothing else.

**The face is `frontend`** (the Dockerfile's `frontend` target, the Next
standalone server): Caddy sends every backend root to `web` and everything else
to it (`deploy/Caddyfile`), and it is an image service beside the pair below.

**AND IT DOES NOT RECREATE `web`, `worker` OR `frontend`.** It reconciles every
other service normally and brings the app pair up with `--no-recreate`, then
says so on its last line. Two consequences, both intended:

* **On a re-deploy the app keeps serving the PREVIOUS tree until step 37.**
  That is the point. This step used to recreate `web` on the new image one
  step before Part 5 could migrate, so every re-deploy served new code against
  an old schema for as long as the migrate took — measured on staging as three
  `reconcile_search_index` failures on a missing column in a four-minute
  window, self-healed by Temporal's retry, which is the belt and not the fix.
  `release.sh`'s header said "within a release there is no way to open it";
  that was true of the release and false of this runbook. **The one recreate in
  a deploy is release act 6**, which sits after act 2's migrate, so the window
  is now zero on both paths.
* **On a FIRST deploy the pair is still created here** — `--no-recreate`
  creates what is absent and leaves alone only what is running — so step 35's
  certificates and step 36's chain are unchanged.

**So step 37 is not optional and never was.** A `provision.sh up` that is not
followed by `./deploy/release.sh` leaves the box on the previous image with
nothing anywhere saying so. If you stop between the two, `docker inspect
$(docker compose -f deploy/compose.yaml ps -q web) --format '{{.Config.Image}}'`
is what tells you which tree is actually serving.

**35. Watch Caddy get its certificates.** **Port 80 is closed, or resets —
there is nothing on it.** With the redirect server off, Caddy binds `:443`
only and ACME validation completes over **TLS-ALPN-01**, which is served on
443 — so nothing needs :80 and nothing listens on it.

Why: `auto_https disable_redirects` (deploy/Caddyfile) tells Caddy not to run
the HTTP-to-HTTPS redirect server, and with no reason left to bind `:80` it
does not — so HTTP-01 is not offered and Caddy negotiates the challenge it can
serve on the port it has. That is the posture a preloaded `.dev` domain wants:
no browser has ever spoken plain HTTP to these names, so there is nothing to
redirect and nothing to listen for.

**The laptop differs and does not test this.** With `CADDY_TLS=internal` there
is no ACME at all — Caddy's own CA signs locally — so the laptop proof can
neither confirm nor break the issuance path. Only a real box does.

```bash
docker compose -f deploy/compose.yaml logs -f caddy | head -50
```

**36. Confirm the chain, from outside the box.**

```bash
echo | openssl s_client -connect "$DJB_ENV.example.invalid:443" \
  -servername "$DJB_ENV.example.invalid" 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

## Part 5 · Release

**Every deploy runs part 5, and part 5 is one command.**

> **`deploy/stage.sh` runs this part for you on a re-deploy**, and it passes
> `--without-alerts` exactly when `deploy/observability/` did not move — which
> is the one act of the seven a caller can key from outside this script. When
> it skips this part entirely (nothing any act is keyed on moved), it still
> probes `/readyz`. See the note at the head of Part 4.

**37. Release.**

```bash
./deploy/release.sh
```

Seven acts, in order, each printed as it happens. `--dry-run` prints the same
transcript with the deployment's own values substituted; the shape below is
illustrative, and the header lines carry whatever this environment actually
resolves to. With an empty `DJB_ACCEPTED_FAKES` the `accepted` line reads
`none` and the seven acts are unchanged.

```
release: DRY RUN — the acts below are what a real run would perform, in this order.
release: project      <compose project>
release: database     <database> on <host>:<port>
release: app role     djb_app (created if absent; the password never leaves the environment)
release: psql client  postgres:18.6  (read from <checkout>/deploy/compose.yaml)
release: tree tag     tree-<12 hex>
release: image        <registry>/djb-web:tree-<12 hex>
release:              sha256:…  (the registry's answer; act 6 pins it into TREE)
release: image        <registry>/djb-worker:tree-<12 hex>
release:              sha256:…  (the registry's answer; act 6 pins it into TREE)
release: image        <registry>/djb-frontend:tree-<12 hex>
release:              sha256:…  (the registry's answer; act 6 pins it into TREE)
release: readyz       https://<SITE_ADDRESS>/readyz  (up to 24 attempts, 5s apart)
release: accepted     2 fake(s) named in DJB_ACCEPTED_FAKES: comms-channel-push comms-channel-sms
release:              act 1 will refuse any of them that is not FAKE right now.
release: [1/7] integrations — the wall: no silent fakes in production
release: [2/7] migrate — the schema, as the schema owner
release: [3/7] grants generate — the release SQL, from the model declarations
release: [4/7] grants apply — the app role's privileges, and the append-only revokes
release: [5/7] alerts apply — the alert route reconciled to the census
release: [6/7] recreate — every image service, onto the new image and the migrated schema
release: [7/7] readyz — wait until the deployment says it is ready
release: nothing was touched.
```

A real run ends `release: RELEASED. 7/7 acts complete.` — and, if the
deployment named any accepted fakes, one more line saying so.

**The exit status is the verdict**, and it is this repository's three: `0` the
release is complete · `1` an act failed, with the act named and nothing after it
run · `2` refused before anything was touched. **Do not pipe it** — it refuses a
piped stdout, exit 2, so a filter can never replace the verdict; redirect to a
file if you want a record.

**Steps 38, 39 and 40 no longer exist as steps.** They were the hand-typed
`migrate`, the `grants.sql.py` generate-and-read, the `psql` apply, and the
restart-and-`curl`; they are acts 2, 3, 4, 6 and 7 of the script, which also
picked up the alert reconcile that used to live in
`docs/runbooks/alerts.md` alone and the integrations wall in front of all of it.
**Nothing after this part was renumbered** — step 41 is still step 41 — because
a runbook whose numbers move is a runbook whose cross-references rot.

**BEFORE ACT 1 THERE IS A REFUSAL THAT IS NOT AN ACT, AND IT IS ABOUT THE
IMAGE.** The box builds nothing (ADR deploy-4), so this script would otherwise
be releasing something it had never checked existed — and compose's answer to a
missing image arrives at **act 6**, after the migrate, with the schema already
moved and the containers still on the previous tree. "Nothing was released"
would then be false. So the question is asked where the honest answer is still
*no act ran*:

* **the registry has no such tag → exit 2**, naming the reference it looked for
  and where the two coordinates live. Either this tree never reached a green CI
  run, or this box is pointed at the wrong registry.
* **the registry and this box's pin disagree → exit 1, naming both.** A tree tag
  is derived from content, so one tag resolving to two digests means somebody
  pushed over it. The pin is what this box last *released* (the `digest` lines in
  `TREE`); the registry is what it would pull now. This is not "could not look" —
  it is a verification that ran and failed, which is `ship.sh`'s exit 1 exactly.
  **Find out which image you meant before re-running anything.**
* **a box with no pin yet is not a disagreement.** A freshly shipped tree has
  never been released here; absence is absence.

**And act 6 pins what it released.** Once `web` and `worker` are actually on the
image, the two digests are written into `TREE` beside the tag — after the
recreate and never before it, or the file would be recording an intention as a
fact. A checkout with no `TREE` marker (a laptop) says so and pins nothing.

**ACT 1 IS THE WALL, AND IT IS THE ACT THIS PART IS MOST LIKELY TO STOP AT.**
`manage.py integrations --wall` reports every external service this deployment
talks to and refuses the release on anything that is not `configured`. A fake is
a stand-in that *succeeds* — the console mail backend accepts every password
reset and prints it to a log; `FakeSmsChannel` accepts every consent-critical
STOP and drops it — so in production it is not a missing feature, it is a silent
one. **Its two failure codes are different questions and the release reports the
number verbatim:** `1` is *this deployment is standing on a fake or an absence*;
`2` is *a seam would not answer, so the census does not KNOW what this deployment
talks to*. "I could not look" is never turned into "it is fine", and exit 2
outranks everything below.

**THE ACCEPTANCE SLOT, AND WHY IT IS PER KEY.** A deployment can have a
legitimate reason to stand on a named stand-in: a template environment ships
`FakeSmsChannel` and `FakePushChannel` and has no gateway to point them at, so
without an escape the runbook could not
be performed on the box it documents. The escape is **`DJB_ACCEPTED_FAKES` in
`deploy/.env`** — whitespace-separated census keys, which `release.sh` expands
into `--accept-fake <key>` arguments and judges nothing about itself:

```bash
# in deploy/.env (vault-managed; provision.sh secrets-put / secrets-fetch)
DJB_ACCEPTED_FAKES='comms-channel-push comms-channel-sms'
```

* **Empty or unset is the full wall**, and that is the default a product keeps.
* It is enumerated **per key against the live census**, so it can never become a
  mode: a key that is `configured`, `not_configured`, or that no row declares at
  all is **refused, exit 1**. You cannot accept an absence, and a **stale**
  acceptance — one whose integration has since become real — must be deleted
  rather than left to quietly cover the next fake that arrives under that key.
* A **new** fake that appears tomorrow refuses the release tomorrow.
* Every accepted key is printed with its detail and its remedy **on every
  release, forever**, and again on the last line. The census's other surfaces —
  `scripts/setup.sh`'s epilogue, the standing prober, the bare
  `manage.py integrations` report — go on calling them fakes, because an
  acceptance is the deploy's verdict and not the census's finding.
* **A product that registers a real transport deletes the key from that line.**
  Leaving it is refused rather than ignored, so nobody has to remember.

"Declared fakes pass" was considered and rejected: every fake this census can see
is declared by construction (`providers.DeclaresFakeness` is the only route by
which fakeness reaches a row), so that rule would have deleted the wall and kept
its name.

**WHY IT IS A SCRIPT NOW, and this is the paragraph worth reading.** This part
always said "every deploy runs part 5, it is idempotent by construction", and
both halves were true. What nobody had said out loud is that a sequence which is
idempotent BY CONSTRUCTION is also **skippable by construction**: nothing
anywhere notices a release that ran three of its four commands. The
manual-seam census ranked this first of every such seam in the tree and
priced it: skip the grants and the application's database role keeps `UPDATE`
and `DELETE` on an append-only table the migration just created — house rule
20's belt, silently unbuckled, with nothing in the gate, the logs or `/readyz`
able to see it. `deploy/provision.sh` is the precedent for the fix and this is
the same demotion: the acts move into a script that can be exit-coded and
driven by a test, and the runbook keeps the reasons.

**WHY MIGRATE RUNS AS THE SCHEMA OWNER.** `POSTGRES_USER` is the RDS master,
which owns the schema; `DATABASE_USER` is the application's role and by design
cannot create a table. Act 1 hands the master's pair over as
`DATABASE_USER`/`DATABASE_PASSWORD` because that is what `config/settings`
reads, in the passthrough form (`-e NAME`, no `=`) so neither value lands in
`ps` or a history file. `DATABASE_URL` is empty in every environment file for
exactly this reason: a URL wins over the parts and would make the override
silently do nothing.

**WHY THE GRANTS ARE RE-APPLIED EVERY RELEASE.** `GRANT … ON ALL TABLES` binds
the tables that exist when it runs. A migration that created a table leaves the
app role with no privileges on it; a migration that created an **append-only**
table leaves the app role holding `UPDATE` and `DELETE` on a ledger. Migrate
then grants, in that order, every time — which is why acts 2 and 4 cannot be
reordered and why act 4 is not optional. The `REVOKE` lines are the append-only
population, **discovered from the model declarations**, never typed — and **act
3 prints the SQL it generated**, because the step this replaced said "generate
the release SQL *and read it*" and reading it is still the point. The output is
deterministic and carries no secret: the `CREATE ROLE` preamble reads the
password with psql's own `\getenv` at apply time.
`deploy/test_grants_census.py` is what holds the emitter to the registry, and it
is run from a checkout:

```bash
uv run pytest deploy/test_grants_census.py
```

**WHY THE ALERT ROUTE IS PART OF THE RELEASE.** `deploy/observability/alerts/apply.py`
reconciles the sink to a census **derived from this tree**
(`deploy/observability/alerts/census.py` walks the code). A release that ships a
new alert-shaped declaration and does not run it leaves the sink reconciled to
the previous tree, and nothing anywhere says so. Its own exit codes are reported
verbatim by the release — `3` the census raised a warning, fix the declaration
first; `2` a required name is missing — so the number is lookup-able in
`docs/product/instruments.md` without re-running anything.

**THE FIRST DEPLOY OF A FRESH ENVIRONMENT HAS NO SINK YET.** The ClickStack
operator account does not exist until a human completes Part 9 step 53, so act 5
cannot run and the script **refuses** rather than skipping — the escape is a
sentence you type on purpose:

```bash
./deploy/release.sh --without-alerts   # then perform Part 9, then re-run without the flag
```

**AND `SLACK_WEBHOOK_URL` IS A SECOND, DIFFERENT REFUSAL — NOT THE SAME ONE.**
It used to sit in the same precondition as the operator account, and
the sentence that one prints is about an account that does not exist yet. On a
box whose sink is **up and keyed** that sentence is simply false, and a refusal
that says something false teaches an operator to stop reading refusals. So it
refuses in its own words: *the sink may be perfectly up; the alert route has
nowhere to deliver.* Reconciling without a URL builds a monitor that **detects
and never delivers**, with nothing anywhere saying so afterwards.

Empty `SLACK_WEBHOOK_URL` disarms **the readyz-prober's own half** — the one
direct alert that cannot ride the sink — and the prober announces that itself,
once per start (`docs/runbooks/alerts.md`; `deploy/compose.yaml`;
`prober.sh`). That contract is untouched. The alert **route** inside the sink is
`apply.py`'s half, and it has no per-start announcement anywhere, which is why
`apply.py` refuses rather than defaults. Fill the vault slot, or type
`--without-alerts` knowing that **on this box it means "route unreconciled", not
"no sink"**.

**READ IT BEFORE YOU RUN IT** — `./deploy/release.sh --dry-run` prints the
project, the database, the app role, the psql client image, the readyz target,
the accepted fakes and the seven acts, and touches nothing.

**WHEN IT STOPS.** The failure line names the act and its exit status, and says
what is true: no act after that one ran. **Fix the cause and re-run the script
from the top** — every act is idempotent, so the acts that already succeeded
repeat harmlessly rather than double. That sentence is driven, not asserted:
`./scripts/test.sh quality/tests/deploy/test_release.py` runs a stopped release and then re-runs it to
completion, along with every refusal and the ordering, against a throwaway
deployment with a stub `docker`.

**THE READYZ WAIT IS BOUNDED AND THE BOUND IS RECORDED, NEVER GATED.**
Act 7 probes up to 24 times, 5 seconds apart — two minutes — from inside the
`readyz-prober` container, with that container's own target, `--connect-to` and
certificate posture. Not a second description of where the deployment lives: the
prober's is the one the alert route already watches, so the release and the 3am
page agree by construction.


**Read those three lines before moving on.** Nothing can check that the address
is the right person, and the command will refuse to run a second time — an
installation has exactly one first tenant. If the address is wrong, the fix is
to start again from an empty database, which is cheap now and expensive later.

`--name` defaults to the part of the address after the `@`, and `--slug` to a
slug of the name; both are worth naming explicitly, because the slug is what
appears in `X-Tenant` headers and in URLs from here on.

**Not `manage.py seed`.** Seed creates a tenant, an owner, a member and a token
with passwords published in this repository, and it refuses without `--force`
when `DEBUG` is off for exactly that reason. `--force` on a real environment is
not the answer; it is the thing the refusal exists to prevent.

## Deploying from CI — the two jobs, and the transport a product builds

**WHAT EXISTS, AND WHAT DOES NOT.** `deploy/stage.sh` is the one deploy
script, run by hand from a checkout or by the two CI jobs described below
(`deploy-staging`, `deploy-prod`), which are in `.github/workflows/ci.yml`;
`quality/tests/test_ci_derive.py` parses them and runs their shell against a
stub `stage.sh`. What is NOT built is the runner-to-box transport (Session
Manager with an ephemeral key, in the role's permissions below): `stage.sh`
reaches a box with plain `ssh`, and a hosted runner holds no key for it — so
a product that sets the variables gets a red step naming the ssh refusal
until it builds that road. The jobs skip with a notice (staging) or refuse
(prod) when the variables are unset.

**Everything above is the hand walk, and it stays the recovery.** This part is
the same acts run by the forge: `deploy/stage.sh` is the one deploy script, so
CI adds a trigger and a credential and nothing else. A deploy from CI and a
deploy from a laptop run the same six acts in the same order against the same
`TREE` marker — ADR deploy-4 (f): promotion is neither a re-tag nor a rebuild.

**The two jobs** (`.github/workflows/ci.yml` is the authority for their exact
spelling; what follows is what they are for):

- **`deploy-staging`** — `needs: [verdict, images]`, runs only on a push to
  `main`, and SKIPS WITH A NOTICE unless the product's variables name a stage
  target and a deploy role, so a clone of the template with no box stays green.
  It assumes the deploy role by OIDC and runs
  `deploy/stage.sh <stage target> --env staging`: pull by digest, migrate (the
  release act, its wall printed as `migrate: <n>s`), recreate, readyz. Its last
  line is the measure: `stage: <tree tag> live in <n>s (migrate <m>s)` —
  `(migrate skipped)` when no release act ran, `(migrate unmeasured)` when one
  ran and printed no wall, never a zero nobody measured.
- **`deploy-prod`** — `workflow_dispatch` with two inputs, `tree` and
  `sanction`. It runs the SAME script as
  `deploy/stage.sh <prod target> --env prod --sanction "<who>: <why>"
  --staging <stage target> --nightly <dir>`, where `<dir>` is the downloaded
  `nightly-leak-proof` artifact — in a product tree (its drawer declares
  `rule_id_namespace:`) the step downloads nothing and hands an empty `<dir>`,
  which `stage.sh` reads as no `--nightly`. It checks out the tree `tree` names (the tree
  staging holds, which a docs-only merge leaves behind main's head) and runs
  THAT tree's own `stage.sh`, so the teeth are the promoted tree's: a tree
  older than the prod gate fails safe, refusing the unknown `--sanction`.
  **Four teeth, all read before the prod box is
  contacted, every red one named in a single exit-2 refusal:** the sanction
  has the `<who>: <why>` shape; staging's `LIVE` marker (`live <tree tag>
  <at>`, which `stage.sh` withdraws before any act that changes a box and
  writes only after act 6's readyz answered 200 — never `TREE` line 1, which
  the ship writes at act 1) names this tree; staging's
  readyz answers 200 (probed from inside its `readyz-prober`, as act 6
  probes); and the nightly leak proof, read by `gate_nightly_read` in
  `scripts/gate_ledger.sh`, is green and no older than 24 h — `nightly:none`,
  `nightly:stale:<at>`, a non-zero `rc=` and an unreadable record are each a
  refusal. A product tree (its drawer declares `rule_id_namespace:`) given
  no `--nightly` prints `a product tree — the platform's nightly leak proof
  is the template's; the product's own gate is its proof (staging proved …)`
  for the fourth tooth and is not refused for it. Staging is only READ;
  nothing is touched anywhere on a refusal.
  **The registry tag is the record** that the tree passed the gate: CI tags
  no tree its verdict did not pass (ADR deploy-4 (b)), and `stage.sh` refuses
  a tree whose image the registry does not hold, so no separate verdict check
  is made. A staging box deployed before the `LIVE` marker existed has none,
  and prod refuses it until one re-stage (readyz only, when nothing moved)
  writes it.
  **Prod is every environment NOT on the declared non-prod list**
  (`DJB_NONPROD_ENVIRONMENTS`, space-separated; default `staging stage dev
  development test qa local`, matched exactly), so `PROD`, `Production` and
  `prod-eu` are gated exactly as `prod` is. The sanction is one printable line:
  a control character in either half, or a half that is whitespace only, is a
  refusal. `--sanction`, `--staging` and `--nightly` are refused for an
  environment on the non-prod list, so a sanction typed at staging is never
  mistaken for one that was checked.

**The product's variables — VARIABLES, NOT SECRETS, the same argument as step
6: they are coordinates.** Placeholders; the job reads them with `vars.`:

```bash
gh variable set DJB_STAGE_TARGET  --body "<ssh destination of the stage box, e.g. ec2-user@<stage host>>"
gh variable set DJB_PROD_TARGET   --body "<ssh destination of the prod box>"
gh variable set AWS_DEPLOY_ROLE_ARN --body "arn:aws:iam::<account>:role/<namespace>-ci-deploy"
gh variable set DJB_DEPLOY_NAMESPACE --body "<namespace>"
# DJB_IMAGE_REGISTRY and AWS_REGION are step 6's and are read as they are.
```

**The deploy role, and its OIDC trust.** `./deploy/iam/product_bootstrap.sh` makes this; the lines below are what it makes. A SECOND role beside step 4's push
role, never a widening of it: the push role writes images, this one deploys
them, and a credential that can do both is the credential a leaked job log
would most like to find. What the runner side of `stage.sh` needs is small —
the box does its own secrets fetch and its own registry login as ITS instance
role (step 19), so the deploy role reads the registry (`provision.sh
image-digest`) and opens the transport to the boxes, and nothing else.

The trust names THIS repository in both `sub` spellings (step 4's argument,

Its permissions, in placeholders — read the two repositories, and reach the

**What a product proves, and what the template proves.** The template has no

(the same drive), and the migrate wall and the release acts
(`quality/tests/deploy/test_release.py`). **Staging live is proven only when an owner
sets the stage variables** — then a push to `main` shows `deploy-staging`
ending on the closing line, and merge → staging live is measured from the push
event to that line. **Prod is proven only by a product**: its first dispatch,
against its own prod box, with a green nightly and staging serving the tree.
A product that has not done that has a refusal drive, not a prod deploy.

## Image scanning — what blocks, what reports, where the SBOM lands

One scanner, trivy, behind one script: `deploy/image_scan.sh <oci-archive | image-ref>`, exit
**0** clean or findings below the bar · **1** a CRITICAL with a fixed version (or an exception that
is malformed or past its date) · **2** could not look (no scanner, no vulnerability database, an
unreadable image). The judgment and the exceptions are `deploy/image_scan_policy.py`; trivy's
version and its release checksums are pinned in the script, and `--install <dir>` fetches exactly
that binary and refuses any other.

**What blocks.** The `images` job in `ci.yml` scans the three OCI archives it built, after the
build and before the hand-off to `images-push`; a 1 fails the job, so nothing is pushed — the
registry holds only scanned bytes (ADR deploy-4 (b)). A HIGH, a MEDIUM, a LOW, and a CRITICAL with
no fixed version are printed and do not block. An archive is scanned for its first platform
(`linux/amd64`); the `arm64` half shares its base distribution and is not scanned separately.

**What reports.** `.github/workflows/nightly-security.yml` derives every image `deploy/compose.yaml`
pins by digest (a `grep` over the `image: …@sha256:` lines, never a typed list), scans each, goes
red when any carries a CRITICAL with a fix, and publishes every image's JSON report as the
`image-scan-reports` artifact whatever happened. Run it by hand with
`gh workflow run nightly-security.yml`.

**A red night is a pin bump.** Read the report for the image that went red, find the publisher's
release that carries the fixed version, and change that one `image: <name>:<ver>@sha256:…` line in
`deploy/compose.yaml` to the new release's multi-arch index digest (house rule 61 —
`docker buildx imagetools inspect <name>:<ver>` prints it); run the stack's selftest unit; open
the PR. One queue row per red night, never a sweep. When no fixed release exists yet, the finding
does not block and the night is not red on it.

**An exception** is a dated line in `deploy/image_scan_policy.py`'s `IMAGE_EXCEPTIONS`: the
vulnerability id, a one-line why, the images it was judged in (the service name for a built image,
the repository's last segment for a pinned one), the date declared and an `until` at most 60 days
later. Past its `until` it is itself a blocking finding naming it — declare it again with a fresh
why, or bump the image.

**Where the SBOM lands.** Each built image's CycloneDX SBOM is written by the same scan and
uploaded on the run as the `sbom-<tag>` artifact, one `sbom-<service>-<tag>.cdx.json` per image;
it lives as long as the run's artifacts do. `images-push` then attests the build's provenance for
every pushed digest (`actions/attest-build-provenance`); verify one with
`gh attestation verify oci://<registry>/djb-<service>@<digest> --owner <owner>`. GitHub holds
attestations only for a public repository or one on GitHub Enterprise Cloud; on a private
repository off that plan the step warns and the push stands unattested.

## Email mechanism

**Not a numbered step, and deliberately so.** Nothing in this runbook plants a
DNS record for mail, verifies a sending domain or waits on a provider's review
clock. **The template never carries production traffic**, so it has no standing
sender and will have none; what it owes the first product is a *mechanism it
can inherit working*, proven once against a real provider and written down here.

### The provider is `EMAIL_BACKEND`, and nothing else is

`apps/comms` sends through `django.core.mail`. Every ESP in this table is a
Django email backend, so choosing one is this setting plus that ESP's
credential — never a code path, never an edit under `apps/`, and never anything
in `config/` (ADR comms-12, narrowing comms-11).

| Provider | `EMAIL_BACKEND` | Credential (environment) | Extra needed |
|---|---|---|---|
| Mailpit / local SMTP | `django.core.mail.backends.smtp.EmailBackend` | `EMAIL_HOST`/`EMAIL_PORT` | — |
| pytest | `django.core.mail.backends.locmem.EmailBackend` | — | — |
| **Resend** | `anymail.backends.resend.EmailBackend` | `ANYMAIL_RESEND_API_KEY` | **`django-anymail[resend]` — already in `pyproject.toml`** |
| Mailgun | `anymail.backends.mailgun.EmailBackend` | `ANYMAIL_MAILGUN_API_KEY` | — |
| Postmark | `anymail.backends.postmark.EmailBackend` | `ANYMAIL_POSTMARK_SERVER_TOKEN` | — |
| SendGrid | `anymail.backends.sendgrid.EmailBackend` | `ANYMAIL_SENDGRID_API_KEY` | — |
| Amazon SES | `anymail.backends.amazon_ses.EmailBackend` | the box's instance role | **`django-anymail[amazon-ses]`, which adds boto3 — the product adds it, not the template** |

`ANYMAIL_<KEY>` variables are discovered by prefix in
`config/settings/base.py`; no ESP is named in that file. `Message.provider`
records what actually carried each message (`anymail:resend`, `smtp`,
`locmem`), so the log answers "who sent this" without anyone reading settings.
`provision.sh preflight` reads the same prefix: its step-24 line names the
`ANYMAIL_*_KEY` or `_TOKEN` slot that is set, or SES on the box's instance role,
or says staging sends no mail and points here. It reads that a key is set,
never that it is valid.

**SES stayed available and did not stay the default.** comms-11 chose it when
the template expected to operate its own sender; comms-12 narrows that decision
to "anymail is the seam" and leaves SES's rejected-alternatives list standing. A
product that needs a BAA its provider will not sign chooses SES, adds
`[amazon-ses]` (and boto3 with it) to its own `pyproject.toml`, and changes one
setting. That is the whole migration.

### The way back: status webhooks

A provider's bounce, complaint and delivery reports arrive at `apps/connections`'
**one** signature-verified receiver — `POST /api/v1/connections/{id}/webhook/` —
and never at a second door (ADR comms-3). Two things are per **connection row**
and not per deployment:

1. **the webhook URL** is that connection's id, so a tenant's provider posts to
   a path nobody else's provider knows;
2. **the signing secret** is `Connection.webhook_secret`, encrypted on the row.
   It is deliberately *not* an `ANYMAIL_*` setting: one deployment-wide signing
   secret would be every tenant's provider sharing one.

For an ESP whose Anymail webhook view declares a signature secret — Resend, via
Svix — the check is the vendor's own, driven through Anymail
(`apps/comms/providers.verify_status_webhook`). For anything else the door's own
HMAC over the raw body stands. Nothing is ever accepted unchecked.

**To wire one up** (Resend; every ESP is the same three moves):

<!-- recipe: connection-create -->
```bash
# 1 · a connection to hold the secret, created through the API as any other is.
#     Runnable as printed — fill WHSEC from the provider's dashboard first.
curl -sS -X POST "https://$HOST/api/v1/connections/" \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d "{\"provider\": \"comms-email\",
       \"name\": \"Resend\",
       \"credentials\": {\"webhook_secret\": \"$WHSEC\"}}"

# 2 · in the provider's dashboard, add an endpoint at
#     https://<host>/api/v1/connections/<connection-id>/webhook/
#     subscribed to FIVE events:
#         delivered · bounced · complained    — what happened to the message
#         opened · clicked                    — what the person then did
# 3 · paste the signing secret the provider shows you into the connection's
#     credentials (step 1's field), and send one message to the provider's
#     bounce simulator.
```

Step 2 is the only part a machine cannot do for you: creating a webhook endpoint
is an account-owner action in the provider's console, and a send-scoped API key
cannot do it.

**Subscribe to `opened` and `clicked` or the engagement half never arrives**,
and nothing will tell you. `apps/comms` records both — one `MessageEngagement`
row per report, readable at
`GET /api/v1/messages/{message_id}/engagement/` and announced as
`comms.message.opened` / `comms.message.clicked` — and the only way those rows
come into existence is this subscription. A deployment that took the three
delivery events and stopped has a working message log, an engagement list that
is empty for ever, and no error anywhere saying why. Following this step
literally without them produces exactly that; the two extra words are the fix.

They are a **different kind of fact** from the three above them, and the API
keeps them apart on purpose: a delivery is something the transport witnessed,
an open is an inference from a request for a tracking image, and on Apple Mail
Privacy Protection that request is made for every message a person receives
whether they look at it or not. So an engagement never moves `Message.status`,
and a product deriving "delivered" from "opened" is deriving a fact from a
guess. Read delivery on the message; read inference on the engagement list.

### What this section does not claim

Deliverability is not proven here and is not the template's to prove. Inbox
placement, DKIM/SPF/DMARC alignment and reputation are facts about a *sending
domain*, and the template has none — the first product proves them on its own
domain with its own DMARC reports. E1′ proved that a message leaves through a
real ESP, that the ESP's own handle is what the row records, and that the
signature and the fork on the way back hold.

## The other transports: SMS and push

**A fresh clone can already send both, and neither of them goes anywhere.**
`apps/comms` registers one transport per channel at import, and for SMS and push
that transport is a **fake**: `FakeSmsChannel` holds the `sms` slot,
`FakePushChannel` holds `push`, each records `provider="fake-sms"` /
`"fake-push"` on every `Message` row it touches and logs at **warning** on every
send. That is deliberate — the whole path is exercised on a laptop from an empty
database with no vendor, no account and no network — and it is also exactly the
shape that goes unnoticed in a deployment, because a fake that works looks like a
transport that works.

**This section is the answer to "so how do I turn the real one on", and it is
here rather than only in a comment beside the code.** The answer used to live
only in `apps/comms/providers.py`, which is not where an operator looks.

### How to tell which one you are running

```bash
# every registered channel, and the class holding each slot
docker compose -f deploy/compose.yaml exec web \
  uv run python manage.py shell -c \
  "from apps.comms.providers import registered_channels; \
   print({k: type(v).__name__ for k, v in registered_channels().items()})"
```

`{'email': 'EmailChannel', 'sms': 'FakeSmsChannel', 'push': 'FakePushChannel'}`
is a fresh clone. Any row still naming a `Fake…` class is a channel whose
messages are being written to the log and delivered to nobody.

The message log says the same thing after the fact: `Message.provider` on a row
carried by a fake is literally `fake-sms` or `fake-push`, so
`GET /api/v1/messages/?channel=sms` answers the question for a deployment nobody
can shell into.

### Turning on the real SMS transport (Twilio)

`TwilioSmsChannel` ships **registered-on-demand, not enabled**, and there is no
setting that switches it on. There could not be one: the credentials are per
**tenant** — a `Connection` row with an encrypted `auth_token` — rather than per
deployment, so the deployment has nothing to read to decide the question, and a
template whose test suite needed a vendor account to send a text would be a
template nobody could run.

Two moves, in this order:

**1 · Put the real transport in the fake's slot**, from *your product's* app
config — never by editing `apps/comms`:

```python
# apps/<your-app>/apps.py
class YourAppConfig(AppConfig):
    name = "apps.<your_app>"

    def ready(self) -> None:
        from apps.comms.providers import TwilioSmsChannel, register_channel

        register_channel(TwilioSmsChannel())      # replaces FakeSmsChannel under "sms"
```

`register_channel` keys on the transport's own `slug`, so this is a replacement
and not a second registration. Re-run the census command above and the `sms` row
should now name `TwilioSmsChannel`.

**2 · Give each tenant its Twilio account, as a connection.** The adapter reads
`account_sid`, `auth_token` (and `from_number`) off a `comms-sms` connection's
encrypted credentials — `auth_token` is both the API credential and the webhook
signing key, because Twilio signs with the account token:

```bash
# POST /api/v1/connections/  as any other connection is created
#   {"provider": "comms-sms", "name": "Twilio",
#    "credentials": {"account_sid": "AC…", "auth_token": "…", "from_number": "+15550000000"}}
```

Then point the Messaging Service's status callback at
`https://<host>/api/v1/connections/<connection-id>/webhook/`, exactly as for the
ESP above. **Do this, or `STOP` is silently dropped**: a person texting STOP
tells Twilio, Twilio refuses the next message with error `21610`, and that
refusal arrives — if it arrives at all — over this callback, where
`record_delivery_status` turns it into a suppression. A deployment on the fake
transport has no way to receive one.

`from_number` is a per-tenant fact and lives on the connection with the rest.

### Turning on a real push transport

The same two moves, with `DevicePushChannel` in place of `FakeSmsChannel`'s twin:

```python
        from apps.comms.providers import DevicePushChannel, register_channel

        register_channel(DevicePushChannel())                          # FCM
        register_channel(DevicePushChannel(provider="apns", path="/3/device"))
```

and a `Connection` per tenant under that provider slug, holding the gateway
credential. Push has **no inbound webhook to configure**: there is no delivery
receipt to subscribe to, so there is nothing in the provider's console to point
at this deployment.

What push has instead of a phone number is an **address book**: a notification
goes to the contact's registered `Device` rows, and a contact with none is a
fail-closed refusal rather than a message that goes nowhere. Devices are
registered through `POST /api/v1/devices/` and retired through
`POST /api/v1/devices/{device_id}/retire/` — both under the `devices` scope
family, so a mobile client's token can be minted with `devices:write` and
nothing else.

**What is not proven here.** The template has no Firebase project and no APNs
certificate, so `DevicePushChannel` has been driven against a recorded
transport rather than against a gateway: the address resolution, the per-device
fan-out, the idempotency key, the credential coming off the encrypted connection
row and the response handling are all exercised, and *"a real gateway accepts
this body"* is not. Treat the first live push as an integration step of your
own, exactly as this runbook treats a sending domain.

### The consent wall applies to all three, and it is not optional

`comms.send()` is the only legal sender in this product — house rule 25, and the
gate refuses a module under `apps/` that imports a mail library — so consent,
quiet hours and suppression are enforced for SMS and push by exactly the machinery
that enforces them for email. A registered device is **not** consent: it says the
product *can* reach the handset, and whether it *may* is the contact's `push`
preference. `POST /api/v1/recipients/{recipient_id}/grant-consent/` with
`{"channel": "push"}` is where that is granted, and `.../suppress/` with the same
body is "stop notifying this person" — as opposed to retiring one device,
which only says that one install is gone.

## Signing a status webhook by hand

**The recipes, because the alternative is reading a test suite.** Every inbound
delivery in this product arrives at one signature-verified receiver
(`POST /api/v1/connections/{id}/webhook/`), and sooner or later you need to send
one yourself: reproducing a bounce a provider will not resend, checking a
deployment's receiver before pointing a vendor at it, or working out whether a
`401` is your secret or your bytes. These were only in
`apps/comms/tests/test_esp_webhook.py` and `apps/connections/tests/test_api.py`,
which is not where an operator looks.

**Sign the RAW BODY BYTES**, in all four schemes. The most common cause of a
`401` that is not a wrong secret is re-serializing the JSON between signing it
and sending it — a re-encode that changes one space changes the digest.

**These recipes are EXECUTED, not proof-read.** Each fenced block below sits
under an HTML comment naming it — `<!-- recipe: house-v2 -->` and its four
siblings — and `quality/tests/test_runbook.py` lifts the block out of
this file at run time and runs it against a live receiver, substituting only the
placeholders the recipe itself names. **The markers are load-bearing: move one,
rename one, or add a fence between a marker and its block, and the drive fails
by name.** Edit a recipe freely — nothing anywhere is a copy of it, so there is

### The body vocabulary, and the one word that means two things

**`message_id` in these bodies is the PROVIDER's handle, not ours.** It is the
string the transport gave us when it accepted the message — what
`GET /api/v1/messages/{message_id}/` returns in its **`provider_message_id`**
field — and it is *not* the message's own id, which is the `{message_id}` in
that path and the `id` in that body. Two different values, and the same two
words name both.

Getting it wrong has one shape: a body
naming our row id verifies perfectly, is stored, and answers **`202`**, because
`202` means *accepted, not processed*. Nothing refuses. The engagement list
stays empty for ever and the only trace is a log line —
**`comms.engagement.unknown_message`** for an open or a click, and
`comms.status.unknown_message` for a delivery or a bounce. Grep for those two
first; they carry `inbound_webhook_id`, so the stored body is right there to
read.

```bash
# the handle to post back, for a message you have just sent
curl -sS "https://$HOST/api/v1/messages/$MESSAGE_ID/" \
  -H "Authorization: Bearer $TOKEN" | python3 -c \
  'import json,sys; print(json.load(sys.stdin)["provider_message_id"])'
```

The rest of the normalised vocabulary, which is what the two house-scheme
recipes below post:

| key | what it is | absent means |
|---|---|---|
| `event_type` | one of `anymail.signals.EventType` — `delivered`, `bounced`, `complained`, `rejected`, `opened`, `clicked`, `deferred`, `queued`… | **absent**: the body carries no vocabulary this deployment can read (`comms.status.untranslatable_body`, with the remedy). **Present but non-terminal** (`deferred`, `queued`): `comms.status.ignored` **naming the word it read**, and the run keeps waiting — that one is the door working |
| `message_id` | **the provider's handle** — see above | a terminal event that names nothing to join on (`comms.status.no_message_id`) |
| `click_url` | the link, on a **`clicked`** event. **The key is `click_url`, not `url`** | the click is recorded with an empty link and **nothing refuses** — the row is legal, the report is wrong |
| `event_id` | the transport's handle for **the event**, not the message. It is what makes a redelivery idempotent | the receiver's own `delivery_id` is used instead, so replays are still deduped |
| `timestamp` | ISO-8601, when the **provider** says it happened | `occurred_at` falls back to now, so a webhook that arrived an hour late reads as an hour-late open |

**Why this table is here and not in the receiver's route documentation.** That
route belongs to `apps/connections`, which verifies signatures and hands the
body on without reading it — its `depends_on` is `core`, `accounts`, `events`
and deliberately **not** `comms`, so it cannot document comms' keys without
inverting the layer contract the whole template is shaped around. The route doc
covers the signature completely, which is the part that is genuinely its own.
The vocabulary is comms' contract, and this runbook is where an operator meets
it.

### 1 · The house scheme, preferred: `X-Signature-V2`

HMAC-SHA256 over `<t>.<raw body>`, where `t` is whole seconds since the epoch,
sent alongside the digest. The timestamp is covered by the signature, and a
delivery whose `t` is more than **5 minutes** from the server's clock is refused
however correct the digest is. This is the scheme this template's own outbound
signer sends, so a product pointing its webhooks at its own receiver speaks one
scheme in both directions.

<!-- recipe: house-v2 -->
```python
import hashlib, hmac, json, time, urllib.request

secret = "…the connection's webhook_secret…"
# `message_id` is the PROVIDER's handle (`provider_message_id` on the message
# row), never the message's own id — see the vocabulary table above. A body
# naming our id verifies, stores, answers 202 and records nothing.
body   = json.dumps({"event_type": "bounced", "message_id": "…"}).encode()   # sign THESE bytes
t      = int(time.time())
digest = hmac.new(secret.encode(), f"{t}.".encode() + body, hashlib.sha256).hexdigest()

request = urllib.request.Request(
    "https://<host>/api/v1/connections/<connection-id>/webhook/",
    data=body,
    headers={
        "Content-Type": "application/json",
        "X-Signature-V2": f"t={t},sha256={digest}",
        "X-Event-Type": "bounced",
    },
)
print(urllib.request.urlopen(request).status)      # 202
```

### 2 · The house scheme, legacy: `X-Signature`

HMAC-SHA256 over the raw body and nothing else. The whole scheme for a sender
that cannot put a timestamp on a request — but it carries **no freshness**, so
those exact bytes keep verifying for as long as the secret lives. **A connection
opened on 2.5.0 or later refuses it** (`timestamped_signature_required`) until
an owner sets `is_signature_v2_required` to `false` through the connection's
signature-scheme route, which is the recipe's first call.

<!-- recipe: house-legacy -->
```bash
# once per connection: accept the body-only scheme (an owner's token).
curl -sS -o /dev/null --fail -X POST \
  "https://$HOST/api/v1/connections/$CONNECTION_ID/signature-scheme/" \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"is_signature_v2_required": false}'
# `message_id` is the PROVIDER's handle (`provider_message_id` on the message
# row), never the message's own id — see the vocabulary table above.
BODY='{"event_type":"bounced","message_id":"…"}'
SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$SECRET" -r | cut -d' ' -f1)
curl -sS -o /dev/null -w '%{http_code}\n' \
  -X POST "https://$HOST/api/v1/connections/$CONNECTION_ID/webhook/" \
  -H 'Content-Type: application/json' \
  -H "X-Signature: sha256=$SIG" \
  -H 'X-Event-Type: bounced' \
  --data-binary "$BODY"                       # 202
```

**Send one, not a hopeful pair.** When `X-Signature-V2` is present it is the
only header consulted: a correct `X-Signature` beside a stale `X-Signature-V2`
is refused, because a scheme a sender can be stepped down from gives you
nothing.

**The receiver takes no bearer and no `X-Tenant`; a client that adds them is
refused `signed_door_takes_no_address`** (403, and `X-Org` the same): the
signature is the credential and the connection names the tenant. That includes
an `Authorization` header a proxy in front of the deployment injects (basic
auth at a wall) — exempt this route from it.

### 3 · Resend, and anything else that signs with Svix

Resend does not use either house scheme: it signs with **Svix**, over
`<svix-id>.<svix-timestamp>.<raw body>`, and the check is the vendor's own,
driven through Anymail (`apps/comms/providers.verify_status_webhook`). The
secret is the `whsec_…` value the provider's dashboard shows you, stored in the
connection's `webhook_secret`. Let the `svix` library — already a dependency —
compute it, rather than reimplementing somebody else's scheme:

<!-- recipe: svix-sign -->
```python
import json, uuid
from datetime import UTC, datetime

from svix.webhooks import Webhook

secret = "whsec_…"  # pragma: allowlist secret — a placeholder; paste the dashboard's value
body   = json.dumps({"type": "email.opened", "data": {"email_id": "…"}}).encode()
msg_id = f"msg_{uuid.uuid4().hex[:20]}"
moment = datetime.now(tz=UTC)                          # a datetime, not an int

signature = Webhook(secret).sign(msg_id=msg_id, timestamp=moment, data=body.decode())
headers = {
    "Content-Type": "application/json",
    "svix-id": msg_id,
    "svix-timestamp": str(int(moment.timestamp())),
    "svix-signature": signature,
}
```

Post those against the same receiver URL. The **body** here is the ESP's own raw
shape (`email.bounced`, `email.opened`, `email.clicked`), not the normalised
`{"event_type": …}` the house schemes take — because with an Anymail ESP
configured there is a translation to read it with, and without one there is not.
That fork is ADR comms-13, and picking the wrong side of it is what
`comms.status.untranslatable_body` in the log means.

### 4 · Twilio

Twilio signs an HMAC-SHA1 over the **callback URL with the POST fields appended
in sorted order**, keyed on the account's auth token, in `X-Twilio-Signature`.
This repository never computes that signature — the SDK's own
`RequestValidator` is the verifier (house rule 43: the vendor validates, we do
not implement somebody else's scheme) — so use the SDK to produce one too:

<!-- recipe: twilio-sign -->
```python
from twilio.request_validator import RequestValidator

url    = "https://<host>/api/v1/connections/<connection-id>/webhook/"
fields = {"MessageSid": "SM…", "MessageStatus": "undelivered", "ErrorCode": "21610"}
signature = RequestValidator("<the account auth_token>").compute_signature(url, fields)
# POST `fields` as application/x-www-form-urlencoded with X-Twilio-Signature: <signature>
```

The URL must be **byte-identical** to the one Twilio is configured with,
scheme and trailing slash included, because Twilio signs the URL it was given.
This deployment builds its side of that string from `PUBLIC_BASE_URL` plus the
receiver's path (`providers.status_callback_url`), so a `PUBLIC_BASE_URL` that
does not match what Twilio actually called — a proxy rewriting the host, a stale
value after a domain move — makes **every** signature fail. That is fail-closed
and deliberate; the fix is the setting, and `comms.sms.signature_refused` in the
log is the line that says so. It is the second most common cause of a `401` here
after the wrong token.

### What a `401` does and does not tell you

It tells you nothing on purpose. Whether the connection exists, whether it has a
secret, what the expected signature was, and whether what failed was the digest
or the freshness window are all withheld — a receiver that distinguished them
would be an oracle. If you get one, check in this order: the raw bytes (did
anything re-serialize the JSON?), the secret (is it the connection's current
`webhook_secret`?), the clock (is `t` current, within 5 minutes?), and the URL
(Twilio only).

A `202` means **accepted, not processed**: the body is stored and handed on. To
see what it became, read the message log, or
`GET /api/v1/messages/{message_id}/engagement/` for an open or a click.

**A `202` and then nothing** is the failure worth naming twice, because it looks
like success from every angle a caller has. It is almost always the
`message_id` confusion above. `comms.engagement.unknown_message` and
`comms.status.unknown_message` in the log are the diagnostic, and the
`inbound_webhook_id` each carries names the stored body so you can read what you
actually sent.

## The verifier boxes — the one hand a human performs

**This is not part of provisioning an environment, and it is here because it is
the only step in this repository that a person must do and an agent cannot.**
Verifier boxes are throwaway EC2 machines a verification runs on; everything
about them — bringing one up, taking one down, baking the image, the census — is
scripted, except the IAM identity that does the bringing up. Minting a
credential needs the account's own credential, so it is yours.

**Three coordinates, from your shell, with no defaults anywhere in the tree.**
An account number and a region are per-deployment facts; a default one shipped
in system machinery is a fact every clone of this template inherits without
being asked. The script refuses — exit 2, nothing created — if any of the three
is unset, and refuses again if the credential resolves to a different account.

```bash
# Read what it would do. No AWS call is made, nothing is created, exit 2.
DJB_DEPLOY_NAMESPACE=<ns> DJB_VERIFIER_ACCOUNT=<12-digit account> DJB_VERIFIER_REGION=<region> \
  ./deploy/iam/verifier_bootstrap.sh

# Do it. Prints the whole plan again, then creates the six things it listed.
DJB_DEPLOY_NAMESPACE=<ns> DJB_VERIFIER_ACCOUNT=<12-digit account> DJB_VERIFIER_REGION=<region> \
  ./deploy/iam/verifier_bootstrap.sh --confirm
```

It creates, and nothing else: policy and user `<ns>-verifier-ops`, role and
instance profile `<ns>-verifier-box` (whose only attached policy is
`AmazonSSMManagedInstanceCore` — never an environment box's role, which reads a
secrets prefix and writes a backup bucket), the egress-only security group
`<ns>-verifier`, and **one** access key. Every one of those names derives from
the namespace and carries `djb:namespace`, so a second product in the same
account creates its own and touches none of yours.

**The access key is printed once, on the last line, and stored nowhere.** Copy
it straight into a profile:

```bash
aws configure --profile <ns>-verifier     # region as above, output json
```

A second run finds all six, reports them as `exists`, creates nothing and mints
no second key. If the secret half was lost, re-run with
`--confirm --rotate-key`. There is deliberately no `--delete`: the six names
above are the whole list to remove by hand.

After that, nothing about these boxes needs you again — the teardown is a timer
inside the image, which is the point.

## Part 8 · Teardown

**Teardown is a step, not an appendix.** `prod` is ephemeral by contract:
provisioned by this runbook, proved, and removed. An environment nobody
can delete in one command is an environment that stays up.

**51. Destroy it.**

```bash

./deploy/teardown.sh --all-mine                    # EVERY project this checkout brought up
./deploy/teardown.sh "$DJB_ENV" --confirm          # an AWS environment
./deploy/dns.sh delete "$DJB_ENV" "$BOX_IP"        # the records, separately and deliberately
```

**`--all-mine` is the reaper, and it is a second-strike fix rather than a
convenience (N112c).** The machine filled up: three laptop deploy stacks, each
with its own ClickStack volume, its own Postgres volume and its own Caddy data,
left behind by rungs that tore down "their" stack and did not know about the
second one they had named by hand for a drill. `teardown.sh local` destroys ONE
project; nothing destroyed the set.

The population is **derived, never typed**, from the same fact `provision.sh up`
reads — Docker's own record of which config file brought a project up. A project
whose `ConfigFiles` names **this checkout's** `deploy/compose.yaml` is this
checkout's, and no other checkout can produce that string. It takes
`--volumes` unconditionally, because the thing that filled the disk was volumes
and a reaper that leaves them is not reaping; it includes **stopped** projects
(`docker compose ls -a`), because a stopped stack's volumes are exactly as large
as a running one's and "it is not running" is why nobody noticed the last three.
It prints `docker compose ls -a` **before and after**, and it removes
`deploy/.env` with them.

`teardown.sh` takes a final RDS snapshot before deleting the instance and gives
the secret a 7-day recovery window. Neither is skippable, and both are there
because a teardown is exactly when somebody discovers they wanted one row.

`teardown.sh local` destroys **only** the project this checkout derives, or a
named one Docker's label proves this checkout brought up. Point it at anything
else — another worktree's stack, a name with no containers behind it — and it
exits 2 naming the project, the directory that owns it and this checkout,
having stopped and removed nothing. A name is not a licence
(`scripts/kill_mine.sh`, refusal 1).

## The backup posture — policy, not cadence

**Run this once per environment, right after `infra`.** It is free, it changes
no data, and it is what stands between a compromised box and its own backups.

```bash
./deploy/provision.sh backup-policy "$DJB_ENV"            # READ-ONLY: what is there now
./deploy/provision.sh backup-policy "$DJB_ENV" --apply    # write the policy, narrow the role
./deploy/provision.sh backup-policy "$DJB_ENV"            # read it back rather than believe it
```

**What it does, and the two things it deliberately does not.** It puts a bucket
policy on `$DJB_DEPLOY_NAMESPACE-<env>-<account>-backups` that DENIES every delete-shaped and
policy-shaped action to every principal except a named retention role (a `Deny`
in a bucket policy beats any `Allow` anywhere, so a later IAM widening still
cannot delete), and denies non-TLS transport; and it rewrites the box role's
inline policy so backups and media are separate statements, neither carrying a
delete, with the backups one saying `BackupsAppendOnlyNoDelete` in its `Sid` so
a future widening has to argue with it.

It does **not** turn on Object Lock — the stronger answer, and the right one for
a product under a retention obligation, deferred because an unchosen retention
period is either useless or a bill nobody agreed to; the trigger to revisit is
named in `provision.sh`'s own header. It does **not** turn on MFA-delete, which
only the ROOT account user with an MFA device can set, cannot be scripted, and
would block legitimate lifecycle expiry.

**And it is not a cadence.** Scheduling backups is the product's.
Policy is not cadence, and leaving one to the product does not leave the other.

**Measured on a real box BEFORE this posture is applied:** the box role can
`DeleteObject` on its own backup bucket — proved against a scratch object the
drill created, never a real dump: the delete succeeded, a delete marker was
written, and `head-object` then 404'd. Versioning kept the bytes, but the box
cannot list versions either, so it could hide a backup it could not then
recover. That is the hole this step closes.

**Measured AFTER, on a fresh scratch object:** `PutObject` OK and `GetObject`
OK — the box must still be able to write and read backups — while
`DeleteObject` and `DeleteBucketPolicy` both come back *"not authorized … with
an explicit deny in a resource-based policy"*. The box can append and cannot
destroy, including the guard itself.

### The break-glass is real, and it will bite you first

**The delete deny applies to the administrator running this script too.** Only
the account **root user** and the (optional) `$DJB_DEPLOY_NAMESPACE-<env>-backup-retention`
role are exempt. That is deliberate — removing a backup should be an act
somebody chose and CloudTrail recorded — but it means *you* cannot tidy a
bucket with your normal credentials, and the first person to discover that will
be whoever tries.

The exemption list is a **condition value, not a principal**, so it may name a
role that does not exist yet: the guard installs today and starts exempting the
retention role the moment a product creates one. (Naming a non-existent role in
`NotPrincipal` is what made the first version of this fail with
`MalformedPolicy: Invalid principal in policy` — AWS resolves principal ARNs at
write time and does not resolve condition strings.)

**To delete something legitimately, widen the list, act, and put it back:**

```bash
B="$DJB_DEPLOY_NAMESPACE-$DJB_ENV-$ACCOUNT-backups"
aws s3api get-bucket-policy --bucket "$B" --query Policy --output text > /tmp/intended.json
# add your own ARN to NoBackupDeletionExceptBreakGlass's StringNotLike list,
# put that policy, do the deletion, then RESTORE by re-running the generator —
# so what lands is this script's output, never a hand-edited file:
./deploy/provision.sh backup-policy "$DJB_ENV" --apply
./deploy/provision.sh backup-policy "$DJB_ENV"          # read it back
```

Assuming the retention role is the better path once a product has created one.

### One thing this step asks rather than assumes

**The box role's inline policy is discovered, not named.** Step 19 above types
a fixed `--policy-name djb-box`; the live environment that first met this step
carried the **namespace-composed** name instead
(`$DJB_DEPLOY_NAMESPACE-$DJB_ENV-box`), because the box had been provisioned by
a hand that differed from the runbook. IAM
policies are **additive**, so a narrowing written under a hard-coded second name
would have landed *beside* the real grant, left `s3:DeleteObject` in place, and
still printed success. `backup-policy` therefore reads
`list-role-policies`, refuses if the role carries more than one, and
**transforms the live document** rather than composing a replacement — a
replacement would also have silently dropped `secretsmanager:DescribeSecret`
and `ListSecrets`, which `secrets-fetch` needs.

## Part 9 · Observability — the sink hears, and the questions are loaded

**Performed right after Part 4, for every environment including the laptop
proof.** ADR obs-2 put the collector and ClickStack in the compose file, so both
containers are already up and the app is already exporting at

accepts any of it.

**WHAT THIS PART IS, AND WHAT IT IS NOT.** The five steps below are **first-run
setup**: they exist once per environment, and every one of them is a human act a
script cannot perform — registering an account in a UI, copying a key the sink
minted, choosing a password. That is the argued-manual class, not the silent
one. The part of observability that *is* per-release — reconciling the alert
route to the census this tree declares — is **not here and is not a numbered
step any more**: it is act 4 of `./deploy/release.sh` (Part 5), so it happens on
every deploy without anybody remembering it, and a release that cannot perform
it refuses rather than skipping. `docs/runbooks/alerts.md` § "Installing the
route" is the narration for that act — the values, the dry run and the

**THE ORDERING THAT FOLLOWS FROM THAT.** On a fresh environment Part 5 runs
before this part exists, so the first release is
`./deploy/release.sh --without-alerts`; perform this part, then re-run
`./deploy/release.sh` with no flag. Every release after that is one command.

## Part 10 · The way back

> **Review tier, and it says so.** Steps 57–60 have been *performed* once, in
> pieces, under pressure: LOAD-1a improvised them out of steps 30, 31 and 34
> when a release stopped at act 1 on a staging box, and the box came back —
> restored to its previous tree, 80/0 migrations, `/readyz` answering with all
> three organs, and the tree hash-verified identical to git. What has never been
> done is *this sequence, in this order, as written*. It is here because the way
> back existing only in one agent's report is the same failure as it not existing
> at all; it is marked so nobody reads it as proven.
>
> **Fresh numbers, and nothing above was renumbered.** A runbook whose numbers
> move is a runbook whose cross-references rot.

**WHEN TO USE IT.** A release stopped, or landed and is wrong, and the fix is to
put the previous tree back rather than to go forward. If the release stopped at
act 1 (the wall) or act 2 (migrate) **nothing was changed** — fix the cause and
re-run `release.sh`; that is not a rollback, it is a retry, and it is the usual
answer.

**WHY THIS IS A ROLLBACK OF *CODE* AND NEVER OF *SCHEMA*, and the reason is a
house rule.** Migrations here are **expand/contract** (house rule 22, enforced
by the gate: no non-nullable `AddField` without a default, no `RunPython`
without a reverse, no drop while the code still references the name). That rule
exists precisely so that **old code on a new schema is a legal state**: the new
migration only *added* things the old code does not know about, and the old code
goes on reading and writing the columns it does know. So the way back is to move
the **code** back and leave the schema where it is. **Migrations are
forward-only.** Do not run a reverse migration to "match" the old tree — you
would be dropping columns the newer tree wrote data into, which is not a
rollback, it is a data loss with a tidy name.

**57. Put the previous tree back.** `ship.sh` left it on the box at
`$DJB_DEPLOY_NAMESPACE.previous` and it is there to be *looked at*, not to be moved by hand —
re-shipping is what makes the landed tree verified against an archive again:

```bash
# from your LAPTOP, in the checkout, naming the tree you are going back to:
./deploy/ship.sh ec2-user@"$BOX_IP" --key ~/.ssh/$DJB_DEPLOY_NAMESPACE-$DJB_ENV.pem --ref <old-sha>
```

`--ref` is the whole difference from step 30. The `TREE` marker carries that
ref's tag, so the image step 59 pulls is the tree that is actually on the box.
Exit 1 means the landed tree does not match the archive and
**nothing was swapped** — the box is still serving what it was serving, which on
a rollback is the broken thing; do not proceed, fix the ship.

**A ROLLBACK IS A PULL AND HAS ALWAYS BEEN ONE IMAGE AWAY.** The old tree's
image is still in the registry under its own tree tag — nothing expires it and
nothing rebuilds it — so going back is resolving a tag that was already green
once. That is the quiet dividend of build-once (ADR deploy-4): the old rollback
re-built the old tree on the box, at 3am, on the machine you were rolling back
*because of*, and a build that failed there left you with neither tree.

**Re-shipping REPLACES `TREE`, so the previous release's `digest` lines go with
it.** That is correct and not a loss: the pin records what *this box* last
released of *this* tree, and after a re-ship this box has released nothing of it
yet. The first release after a rollback therefore has no pin to disagree with,
exactly as a first deploy does.

**58. Re-materialize the environment** — step 31 again, verbatim, and for step
31's reason: `ship.sh` does not carry `deploy/.env`, and a hand-copy loses the
group the containers read it as.

```bash
./deploy/provision.sh secrets-fetch "$DJB_DEPLOY_NAMESPACE/$DJB_ENV/" deploy/.env
ls -ln deploy/.env      # group 10001, mode -rw-r-----
```

**59. Pull the old image and bring it up** — steps 33 and 34 again. `provision.sh
up` compares the env file's pin against this box's `image-tag`, **adopts the
tree's tag** and **pulls** it, which is what stops a rollback from starting the
image you were rolling away from:

```bash
cd ~/"$DJB_DEPLOY_NAMESPACE"
export DJB_IMAGE_TAG="$(./deploy/provision.sh image-tag)"
echo "$DJB_IMAGE_TAG"                   # must be the OLD tree's tag now
./deploy/provision.sh image-digest web  # exit 2 here = the old image is gone from the registry
./deploy/provision.sh up
docker inspect $(docker compose -f deploy/compose.yaml ps -q web) \
  --format '{{.Config.Image}}'      # must end in the tag above
```

**`image-digest` refusing here is the one rollback failure worth naming in
advance**: it means a registry lifecycle rule expired the old tree's image. A
rollback then has nothing to go back *to* — and that is a policy to fix in the
registry, not on the box.

**60. Release from the top.** Part 5, unchanged and in full — the wall, then the
grants, then the restart, then `/readyz`. It is safe and it is not optional:
act 4 re-applies `GRANT … ON ALL TABLES`, which binds *the tables that exist when
it runs*, and the tables that exist are the newer schema's. Skipping it leaves
the app role holding `UPDATE` and `DELETE` on whatever append-only table the
migration you are rolling away from created.

```bash
./deploy/release.sh
```

**WHAT THIS DOES NOT COVER, declared rather than discovered.** It does not undo
a migration (above, and deliberately). It does not undo anything the newer code
*sent* — an email, a webhook, a message to a provider — because nothing can. It
does not restore data: that is `docs/runbooks/backup-restore.md`, a different
decision with a different blast radius, and the two must not be run as one
motion. And it assumes the previous tree is a tree you can name; if you cannot,
step 57 has nowhere to go and the answer is the backup runbook.
