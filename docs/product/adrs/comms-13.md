# ADR comms-13

**A drop is a judgement, and it says which one (ADR comms-13; decomposed as "comms-10", a number the temporal-lever ruling above already holds — same ADR, next free number):** the status vocabulary on the template-HMAC path is **anymail's normalised shape and nothing else**, because with no Anymail ESP configured there is no translation to read a vendor's raw body with — `{"event_type": …, "message_id": …}` is the door's contract there, and a raw `{"type": "email.bounced", …}` is a language that deployment cannot read. The three ways a status body can produce no status are three findings for three different people, and each now carries **its own log name and its own remedy**: `comms.status.ignored` fires **only** for an event that was read and understood as non-terminal and always prints the word it read (the door working, the run still waiting); `comms.status.untranslatable_body` for a body carrying no vocabulary this deployment can read, naming both ways out — post the normalised event, or set `EMAIL_BACKEND` to an Anymail ESP — which is a **deployment** fault; `comms.status.no_message_id` for a terminal event naming no handle to join on, which is a **provider** fault. One name over three causes is exactly the shape a nameless drop used to take: `ignored` with an empty `event_type` claimed a judgement nobody had made, the message stayed `sent` forever, and the field test spent its first two days on the worker. **The account of a drop is the adapter's, like the status itself** — `ExplainsStatusDrops` is an *optional second protocol* beside `ChannelProvider`, so a product transport that never grows it still never produces a nameless drop (the door falls back to what it can read for itself, and that fallback is driven by a test rather than hoped for). And `scripts/mail_demo.py` **speaks the contract it drives**: it already asked which signature scheme the stack arms, it now asks the same question of the *body* — normalised on `hmac`, raw ESP on `svix` — and leg 4's failure names both indistinguishable causes (read-and-dropped, with the log names to grep; or never-processed) instead of blaming the worker first. Rejected: guessing the ESP from the connection slug (the provider is `EMAIL_BACKEND` and nothing else — comms-12); refusing an unreadable body with 4xx (verify→store→202 is settled in comms-3, and a 4xx would make somebody else's malformed payload our door's problem); valving the comms doorless trio here (ADO-8 — a valve without the paired `quality/rules.yaml` tighten kills rule 42's canary at the merged tree, the a0da0bd class, and the coordinated close is a residual for a rung allowed both files). trigger to revisit: a product's relay cannot normalise — it implements `normalize_status` and `explain_status_drop` on its own adapter, which is what both protocols sit on the seam for.
