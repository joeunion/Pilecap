# ADR platform-1

**ADR platform-1 · context:** the repository was renamed to `example.invalid` and the old name was still a literal in seven places — settings, two compose env defaults, `.env.example`, the devcontainer's display name, the README heading — so a product renamed by editing each surface it happened to find, and Zitadel had already materialised the ones it missed · **decision:** ONE canonical env-backed setting, `PRODUCT_NAME` in `config/settings/base.py` (default `"Pilecap"` — the template's own name, so a fresh clone is honest about being the template), and every surface that *shows* or *materialises* a name derives from it: `ZITADEL_PROJECT_NAME` defaults to it, and BOTH compose files — `compose.yaml` for development and `deploy/compose.yaml` for a deployment — interpolate `${PRODUCT_NAME:-Pilecap}` into the first instance's org name (unless `ZITADEL_ORG_NAME` names one) and its service account's display name; an empty `PRODUCT_NAME` reads as unset in settings and in compose alike. A product sets it once in `.env` (a deployment in its environment file) · **rejected:** hardcoding the name per surface (what was there — every rename is a survey, and the surface you miss is the one a console shows a customer six months later); deriving it from the directory or the git remote (a worktree and a fork are different directories with the same product) · **exception, deliberate:** `compose.yaml`'s `name: djangobootstrap` does NOT derive — it is infrastructure identity, containers and volumes key on it, and changing it orphans a running stack and its data. Neither do the Zitadel *logins* (`ZITADEL_ADMIN_USERNAME`, `ZITADEL_DEV_USER_EMAIL`, `ZITADEL_MACHINE_USERNAME`): they are account identifiers already created, and renaming one is a migration, not a setting · **renaming an instance that already materialised the old name:** teardown + fresh bootstrap (drop the `zitadel` database and the `zitadel_bootstrap` volume, re-run `./scripts/setup.sh`), which re-materialises from these defaults and doubles as the from-zero rebuild test — NOT a rename against the management API. `zitadel_seed` finds-or-creates by name (`accounts.zitadel.ensure_project`), so a changed name on a live instance makes a SECOND project with fresh client ids while `.env`'s `ZITADEL_CLIENT_ID` still points at the old one (owner ruling) · **not covered:** `README.md`'s heading and `.devcontainer/devcontainer.json`'s `name` are text no variable reaches, so a product edits those two by hand; each now says so at the line · **amended 2026-08-26 (owner ruling):** the identity a stranger reads becomes **Pilecap**, so the default value above moves from the template's former name to `"Pilecap"` — the *mechanism* is untouched and is exactly how that rename executed (one setting, derived surfaces, two hand-edited lines). The infrastructure namespace stays: the compose project name quoted in the deliberate exception above, the `DJB_` environment prefix and the `djb_` database prefix are covered by this row's own deliberate exception, because renaming them orphans running stacks and their data, staging included. This supersedes the earlier census recommendation to keep the former name (its leak argument was put to the owner verbatim and overruled) · **wire identifiers are not display identity:** the MCP `serverInfo` name (`config/mcp.py`) and the outbound `User-Agent` tokens (`apps/connections/client.py`, `apps/accounts/zitadel.py`) were renamed as lowercase **literals** and do NOT derive from `PRODUCT_NAME` — a display name may legally carry spaces and mixed case, and a wire token derived from one is malformed the day a product sets it · trigger to revisit: a third surface needing the name at *runtime* (an admin site header, an email from-name) — then it reads `settings.PRODUCT_NAME`, and this row is where that is already decided. Read *display* surface there: the wire-identifier clause above is the boundary that trigger stops at.
